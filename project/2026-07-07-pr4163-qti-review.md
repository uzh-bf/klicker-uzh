The real assets are the **OpenOLAT-validated QTI 2.1 templates and example packages** — extract those and rebuild the export as an integrated TypeScript feature. ## 1. What the PR actually contains

Everything lives in a new standalone `packages/qti/` directory:

| Part | Files | Purpose |
| --- | --- | --- |
| Generator script | `main.py` (260 lines) | Renders Jinja templates from a **hardcoded** `ITEMS` list (main.py:93) |
| Templates | `templates/*.xml.jinja` (7 files) | QTI 2.1 item/test/manifest templates for SC, MC, KPRIM, FREE_TEXT, NUMERICAL |
| Examples | `examples/{test,olat_export_test,olat_export_qbank,ai_generated_qti,quizgen}/` | Reference exports from OLAT + generated output |
| Schema | `imsqti_v2p1p2.xsd` (10,475 lines) | Official QTI 2.1 XSD (validation code is commented out) |
| Preview viewer | `out/qti.js` (5,702 lines minified) + `out/theme/`, `preview.js` | Vendored third-party QTI.js viewer (© 2018 Brian Mottershead, v0.1) served by a bare Express static server on port 8080 |
| Python tooling | `pyproject.toml`, `poetry.lock` | Poetry project, Python ^3.12, deps: jinja2, lxml, markdown, json2xml, eq-quizgen |

**What it does NOT contain, despite the PR's framing ("element import/export and QTI"):**

- No **import** direction at all (no QTI parser, no upload handling).
- No connection to Klicker data — questions are hardcoded Python dicts, not read from the DB/GraphQL.
- No UI, no GraphQL mutation, no download endpoint. A lecturer cannot reach any of this.
- No tests, no CI wiring, no README.

## 2. Findings

### 2.1 Stability

1. **Branch unmergeable and stale.** `git rev-list --count origin/QTI..origin/v3` = **1197**; GitHub `mergeable: CONFLICTING`, `mergeStateStatus: DIRTY`. `pnpm-lock.yaml` alone has +1994/−343 lines of churn. The repo has since gained `response-api`, Hatchet workers, Playwright, etc. — the integration surface this prototype would have targeted has moved substantially.

2. **XML escaping is effectively OFF — any `&` or `<` in question content produces a broken export.** `main.py:237` uses `select_autoescape()`, which decides based on the template file extension. All templates end in `.jinja` (e.g. `itemSC.xml.jinja`), so the extension check sees `jinja`, not `xml`, and autoescaping is disabled. Verified empirically:

   ```python
   from jinja2 import select_autoescape
   select_autoescape()('itemSC.xml.jinja')  # -> False
   select_autoescape()('itemSC.xml')        # -> True
   ```

   Consequence: `{{item.title}}` (item.xml.jinja:3), `{{item.content}}` (itemSC.xml.jinja:17), and `{{option.content}}` (itemSC.xml.jinja:22) are interpolated raw. A question titled `Supply & Demand` or an option containing `x < y` yields malformed XML that OLAT will reject. Note that simply turning autoescape on is also wrong: `item.content` is markdown-rendered HTML that must land in the XHTML item body unescaped, while titles/options need escaping. The fix is a deliberate per-field strategy, which the prototype never got to.

3. **Naive `$$` LaTeX handling corrupts content.** main.py:43-44 does `content.replace("$$\n", "$$").replace("$$", "$")` — any literal dollar sign in question text (e.g. "costs $5") gets mangled, and `$$…$$` display math semantics are collapsed into inline `$…$` by blind string replacement.

4. **XSD validation exists but is commented out** (main.py:6-17). The one guardrail that would catch findings 2-3 at generation time is disabled.

5. **Committed examples are stale.** `examples/test/itemSC.xml` and `itemMC.xml` both contain `<div>Which animals can fly?</div>` as the question body, which does not match the `ITEMS` content in `main.py` (Meaning of Life / The Sun). The examples were generated by an earlier version of the script, so they can't be trusted as "current output".

6. **Dead/buggy code:** `process_sc_item` (main.py:29) is never called and would return a lazy `filter` generator instead of a value. `eq-quizgen` and `json2xml` are declared deps but unused in `main.py`.

7. **CWD-dependent paths** (`FileSystemLoader("./templates")`, `out/...` at main.py:237,245,252,260) — script only works when run from `packages/qti/`.

### 2.2 Security

Current exposure is low because nothing is user-reachable, but for productionization:

1. **XML injection via unescaped interpolation** (same root cause as stability finding 2). Once the export runs on real lecturer content, a crafted question could inject arbitrary XML into the exported package (e.g. altering `responseProcessing` scoring). Severity is moderate — lecturers export their own content — but shared question pools and institutional trust in exported packages make escaping-by-construction mandatory.

2. **Vendored minified third-party viewer.** `out/qti.js` is 5,702 lines of minified JS from an unmaintained 2018 project (v0.1). Unauditable, unpatchable, committed to the repo with `.gitignore` exceptions (`!packages/qti/out`). Fine for a local preview hack; must not ship or persist in the repo.

3. **The future import path is the actual security-critical surface** and doesn't exist yet. When it's built it needs, at minimum: hardened XML parsing (entity resolution and DTD loading disabled — XXE; lxml: `resolve_entities=False, no_network=True, load_dtd=False`, or in Node use a non-DTD parser like `fast-xml-parser`), zip-slip-safe extraction of QTI packages, file-size and entry-count limits, and MIME/type validation on upload. Treat the import as its own PR with its own security review.

4. **Operational surface:** introducing a Python/Poetry runtime into a Node-only production stack doubles the patching/build/deployment surface for one feature. The preview Express server (`preview.js`, port 8080, no auth) is dev-only and fine as such.

### 2.3 Quality

- Python package inside a pnpm/Turborepo monorepo: invisible to `pnpm run check/lint/build`, no CI coverage, no lint/typecheck/tests. SonarQube quality gate on the PR: **failed**.
- Python 3.12-only syntax (nested same-quote f-strings, main.py:71) with no version guard beyond pyproject.
- ~16.5k of the ~22.9k added lines are vendored artifacts (XSD 10,475 + qti.js 5,702) — the PR is unreviewable by size, but the hand-written core is only ~1,000 lines (main.py + templates).
- No README; pyproject references one that doesn't exist.

### 2.4 UX

There is no UX yet — no entry point in `frontend-manage`, no GraphQL op, no download flow, no i18n strings. The preview viewer is localhost-only tooling. This is expected for a spike; it just means "remaining UX work" is *all* of it (see roadmap).

### 2.5 Usefulness — why this is worth continuing

- **High product value for UZH:** OLAT is the university's LMS; lecturers repeatedly ask to reuse Klicker question pools in OLAT exams. This is the "content portability" backlog item (ClickUp 86caazdjz).
- **The templates encode real, hard-won knowledge.** They were iterated against actual OpenOLAT imports (commit 88b505f: "change version to OpenOLAT 6.1.0 to ensure import works") and cover all five Klicker element types, including the OLAT-specific KPRIM `correctResponse` convention (`"opt0 correct" / "opt1 wrong"` value strings) and manifest `interactionType` metadata. Reverse-engineering this from scratch would take days; the `examples/olat_export_test/` corpus (a real OLAT export) is the reference oracle.
- QTI 2.1 remains the right target: OpenOLAT still imports QTI 2.1 packages (QTI 3.0 adoption is not relevant for the OLAT use case).

## 3. Recommendation

**Close PR #4163 (keep the `QTI` branch as reference), and rebuild the export as a TypeScript feature on a fresh branch from `v3`.** Rationale: the branch cannot be reasonably rebased across 1197 commits; the Python runtime is the wrong home for a production feature in this stack; and everything worth keeping (templates, examples, XSD, markdown/LaTeX learnings) is data, not code, and transfers cheaply.

## 4. Roadmap to production (execution plan)

Each phase is a separate PR from `v3`. Work through them in order; don't start a phase before the previous one's acceptance criteria are met.

### Phase 1 — Core export library (TypeScript), no UI

**Goal:** a pure function `generateQtiPackage(elements: Element[]): Buffer` (a zip) inside a new `packages/qti` **TypeScript** package (or inside `packages/util` if we want to avoid a new package — ask Roland before creating one).

Steps:

1. Copy `templates/`, `examples/`, and `imsqti_v2p1p2.xsd` from the `QTI` branch as reference material: `git checkout origin/QTI -- packages/qti/templates packages/qti/examples packages/qti/imsqti_v2p1p2.xsd` (adjust destination paths).
2. Re-implement each Jinja template as a typed function that **builds XML programmatically** (e.g. `xmlbuilder2`, already-safe escaping by construction) instead of string templating. Keep the exact element/attribute structure of the reference templates — they are OLAT-validated; do not "improve" the QTI structure.
3. Handle the two content channels explicitly:
   - `title`, option `content` short texts: plain text, escaped (the XML builder does this for you).
   - question `content`: convert Klicker markdown to XHTML using the existing markdown pipeline (`packages/markdown`) and inject as parsed XML fragments, not as a string. Decide LaTeX handling deliberately (see open question below) — do **not** copy the `$$` string-replace from main.py:43-44.
4. Map Klicker element types from the Prisma schema (`packages/prisma`) to the five templates: SC, MC, KPRIM, NUMERICAL, FREE_TEXT. Skip/flag unsupported types (e.g. FLASHCARD, CONTENT) with an explicit "skipped" list in the return value — never silently drop.
5. Package as zip: `imsmanifest.xml` + `test.xml` + one `<identifier>.xml` per item (structure per `examples/olat_export_test/`).

**Tests (vitest, same package):**

- Golden-file tests: generate from fixture elements, assert against checked-in expected XML.
- **XSD validation test:** validate every generated item against `imsqti_v2p1p2.xsd` (e.g. via `libxmljs2` or a CI-only validation step). This resurrects the commented-out validation from main.py:6-17 as a permanent guardrail.
- Adversarial-content tests: titles/options/content containing `& < > " '`, `$5`, `$$x^2$$`, umlauts, emoji, very long strings. Every output must remain schema-valid.

**Acceptance criteria:** `pnpm --filter @klicker-uzh/qti test` green incl. XSD validation; adversarial contents produce valid XML; package builds in turbo pipeline (`pnpm run check` covers it).

### Phase 2 — Backend integration (GraphQL mutation + download)

1. Add a `exportQuestionsQti(elementIds: [Int!]!)` mutation in `packages/graphql` (Pothos, three-layer auth: authenticated lecturer, owns all requested elements — follow an existing export/download resolver as pattern).
2. Upload the zip to blob storage the same way existing image/file uploads work; return a signed download URL. Do not stream large binary through GraphQL.
3. Regenerate ops (`pnpm --filter @klicker-uzh/graphql generate`).

**Acceptance criteria:** mutation rejects elements not owned by the caller (write a test for this); returns a working download URL; exported zip imports cleanly into OpenOLAT (manual check, see Phase 3 checklist).

### Phase 3 — UI in `frontend-manage` + real OLAT verification

1. Question-pool view: add multi-select → "Export to OLAT (QTI 2.1)" action. Follow existing bulk-action patterns in the question pool. i18n strings in `packages/i18n` (de + en).
2. Show the "skipped unsupported elements" list from Phase 1 in the result dialog so lecturers aren't surprised.
3. Verify with `agent-browser` (delegated login, lecturer/abcd) — before/after screenshots into the PR.
4. **Manual OLAT verification checklist (must be executed and documented in the PR):** import the exported zip into OpenOLAT (staging), one question of each of the 5 types, check: renders, correct answers score correctly, KPRIM scoring matches OLAT convention, math/formatting renders, umlauts intact.

**Acceptance criteria:** screenshots + completed OLAT checklist in PR description.

### Phase 4 — QTI import (separate, later, security-review mandatory)

Out of scope until export ships. Requirements gathered now: hardened XML parsing (no DTD/entities/network), zip-slip-safe extraction, size/entry limits, map QTI 2.1 items → Klicker elements with an explicit per-item success/failure report, reject-don't-guess on unsupported interaction types. Budget a dedicated security review before merge.

### Open questions for Roland (blockers before Phase 1 step 3)

1. **LaTeX in OLAT:** how should Klicker `$$…$$` KaTeX content be represented so OpenOLAT renders it? (OLAT supports LaTeX in QTI content; verify the exact delimiter/element convention against a manual OLAT-authored item containing math — export one from OLAT and inspect, like `examples/olat_export_qbank/` was made.)
2. **Images:** Klicker content references blob-storage URLs (see the SC example in main.py ITEMS). Should exports embed images in the zip (QTI-proper, works offline) or keep absolute URLs (simpler, breaks if storage moves)? Recommendation: embed.
3. New package `@klicker-uzh/qti` vs. folding into an existing package.

## 5. Salvage / drop list (from branch `QTI`)

**Salvage (copy into the new work):**
