# Live quiz rewards after delayed answer processing

## Approval summary

Status: direction-only proposal; implementation has not started. The user approved planning after the separate execution-safe close correction. This plan does not authorize reward schema changes, worker changes, migration, repair of historical awards, merge, deployment or a stack-topology change.

An answer received before a block closes can finish processing after the lecturer ends the quiz. The current end transaction awards one Redis snapshot. Delayed aggregation repairs results and session scores, but cannot repair course points, XP or daily timeline entries without risking duplicate awards. The existing five-minute wait is a heuristic, and the application has no accepted-work completion barrier.

Recommend retaining the current synchronous end action and existing Redis/Hatchet processing, then recording the reward contribution already applied for each quiz execution and participant in PostgreSQL. The existing end transaction would use that record; existing delayed handlers would reconcile a later authoritative snapshot by applying only its difference. Repeating the same snapshot would do nothing. A real generation identity must also travel with accepted response work, so an old run cannot affect a reset quiz. This introduces a focused accounting record, not another authentication/session system.

The main unresolved product choice is rank achievements: late answers can change the winning participants. Recommend correcting each execution's recorded rank award and bonus to its current result, rather than leaving early winners permanently favored. Reset would reverse that execution's recorded contribution exactly once. Both need explicit approval because they can decrease a previously shown bonus or count. The first implementation should cover newly started executions only; historical reconciliation remains separately authorized because older aggregate totals do not prove which awards were already applied.

Success requires controlled PostgreSQL/Redis/Hatchet fault and retry tests plus browser evidence that ending remains immediate and pending reconciliation recovers. Passing source tests alone is insufficient. The required configured final review remains unavailable and separate from this planning consultation.

## Evidence and limits

The source baseline is the existing Control stack. The close fix is at API commit 32d1252200a7ecdc1a8a67e1003eaeb95e6192fa; the previously published integrated top is a6606658648b5a312b1bcc07961b0b543b975cb2. The later audience changes do not alter reward processing. Exact future delivery heads must be recorded when implementation is approved.

- `endLiveQuiz` in `packages/graphql/src/services/liveQuizzes.ts` claims the terminal quiz transition, reads the points/XP hashes and increments durable totals in one transaction. An already-ended quiz returns early. This prevents double ending, but does not establish processing completeness.
- Delayed standard aggregation calls `updateLiveQuizBlockResultsFromCache`; its SESSION score upserts in `packages/util/src/blocks.ts` do not record course, XP, timeline or achievement contributions. Assessment aggregation uses persisted responses for results and cache data for scores. Its existing failure paths and downstream retries need focused qualification before being used as an accounting guarantee.
- `LiveQuiz` has a stable ID and namespace, and `ElementBlock` has an execution counter and activation time. Abort/reset increments block execution; the inspected code does not rotate quiz namespace. A stable quiz ID or namespace alone cannot distinguish runs.
- Regular response events contain a message ID, quiz ID, instance ID and receipt timestamp. Assessment correlation data contains execution, but `apps/response-api/src/index.ts` does not forward it into the worker event. Queued work must not choose its generation from whatever Redis metadata exists when it eventually runs.
- Session score rows exist per participant and quiz. Participant XP, course totals, timeline totals and achievement counts are aggregate records. They cannot reconstruct a missing per-execution receipt. Assessment response/correction records are useful evidence, but do not supply a uniform standard-quiz accounting record.

These are source findings plus the supplied independent synthetic review. The close-race tests exercise real PostgreSQL with synthetic cache clients; they do not prove a live Hatchet backlog, historical reward discrepancy, or absence of other worker delivery defects. No production or personal records were inspected for this plan.

## Alternatives and recommendation

| Approach | Change and benefit | Material limit |
| --- | --- | --- |
| Accepted/processed barrier | Register every accepted response and terminal outcome; postpone final rewards until all accepted work drains | No barrier exists today. It must handle enqueue failure, retries, rejected responses, anonymous work, reset and crashed workers. A timer or queue-length check is insufficient, and reward availability changes. |
| Durable applied contribution — recommended | Keep immediate end; transactionally record and reconcile each execution's already-applied points, XP, timeline and rank award | Requires one focused data model change, generation fencing and trustworthy source snapshots. It must not promote stale or duplicate Redis increments to authoritative rewards. |

The contribution approach handles repeat/reordered reconciliation and end-versus-worker races without holding a user request open. It does not establish processing completion or by itself make response ingestion reliable. A cache snapshot may be used only after the existing worker's per-response application is proven idempotent and bound to the same execution. Assessment paths that currently increment on duplicate aggregation must gain a minimal correlation receipt before their snapshots can drive durable differences; a contribution ledger cannot correct an inflated source total.

## Proposed implementation boundary

Main owns lifecycle identity, reward semantics, migrations, rollback and acceptance. Keep the current Control stack unchanged until a separately approved implementation package determines its owning existing layer or follow-up boundary. Do not silently add a seventh layer or a separate PR.

Use the existing `liveQuizzes.ts` end/reset/aggregation paths and response API/worker messages. Add one narrowly shared reconciliation entry point only because end and the delayed handlers are concrete callers. Reuse existing reward arithmetic, participant/course restrictions and daily timeline operations after adapting them to accept the original contribution date. No dependency or replacement queue is proposed.

One schema-aware generated migration should introduce only the necessary execution identity and contribution/receipt state. Resolve whether the existing block execution vector plus quiz start is sufficient or one explicit quiz-run token is smaller and safer. Prefer one explicit token shared across the run if it avoids a vector in every receipt; do not repurpose the long-lived embed namespace. The concrete schema and uniqueness constraints require independent review before implementation publication. Additional ordered migrations are warranted only by an actual expand/rollout dependency, not by arbitrary slicing.

For each accepted response, capture the run and block execution at admission and preserve the receipt timestamp. The worker verifies that identity before effects. Rejected or old-generation work cannot increment current rewards. Standard and assessment source reward increments must be once per accepted response identity; an assessment database response followed by failed Redis application must be recoverable rather than treated as finished solely because a response row exists. Preserve the established retry/cutoff rules and do not acknowledge an enqueue failure as recorded success.

Generation validation, response-identity deduplication, reward increments and source-version advancement must form one atomic Redis operation. A pipeline with independently successful commands is insufficient. Read points, XP and their source version as one coherent snapshot; PostgreSQL locking alone cannot serialize Redis writers. On ambiguous success, a retry must observe the receipt and avoid a second increment. Partial cache/command failure must remain unknown and recoverable, never become a zero snapshot.

For each participant, reconcile the current eligible snapshot with the stored applied contribution inside a transaction serialized on the quiz execution. Compute the difference; update participant XP, course score, the original daily timeline and any rank contribution, then save the new receipt in the same transaction. If any write fails, everything rolls back. Repeating a snapshot or concurrent end/reconciliation cannot award twice. Reordered jobs must fetch current authoritative state after acquiring the reconciliation lock or reject older snapshot versions; they must not apply a stale decrease.

A successful reconciliation version records only that snapshot; it does not mean all accepted work finished. Every later atomic source-version change must trigger reconciliation through the existing task infrastructure. If that signal is lost, bounded recovery compares source and applied versions. Failure propagates through the existing task retry contract and keeps required source evidence.

Cache cleanup needs its own explicit safe predicate: the execution is sealed against new admissions, every accepted response has a proven terminal outcome, and the final coherent source version has been durably reconciled. Until that can be established, keep source evidence and report the unresolved execution rather than applying the existing one-day expiry. Missing or partial hashes after expiry cannot justify negative differences or recovery claims. The implementation must qualify the minimal accepted-work receipt needed for this predicate; if the available source cannot prove it, stop before enabling automatic cleanup. Reconciliation alone is not a substitute for this completion evidence. A bounded recovery mechanism must revisit ended executions with unapplied changes after retry exhaustion; the design must specify its owner, cadence and terminal error without indefinite quiet failure. Reuse existing task infrastructure if a supported reconciliation sweep exists; otherwise propose that single recovery job explicitly rather than adding one silently.

Reset requires a separate ruling below. If reversal is approved, subtract the stored execution contribution and rank count in the same guarded reset transaction, mark its receipt reversed, then advance generation and reset quiz data. Retrying reset is a no-op for the old contribution, and old worker messages cannot recreate it. Existing manually corrected assessment contributions must reconcile to their authoritative corrected amounts; do not award the original response points again.

## Decisions before reward implementation

1. **Rank changes after end.** Recommend reconciling this execution's rank achievement and associated bonus to the corrected standings. Alternative: make ranks provisional and award them once after a real completion barrier. Keeping a wrong award forever preserves a known inconsistency and is not recommended.
2. **Reset.** Recommend reversing only the recorded old execution's XP, course points, timeline and achievement contribution before a new run. This can reduce totals and needs explicit approval; it must never guess a reversal for an older run without receipts.
3. **Eligibility and date.** Choose one eligibility time for every permanent participant: end-time, as today, or admission-time for everyone. Do not mix the two for late discoveries. Recommend retaining end-time semantics only if accepted-work identity identifies every potentially late participant in time to freeze their participation at end. If that proof is unavailable, present an explicit admission-time behavior change before implementation. Store XP eligibility separately and apply differences to the original reward date. The timeline helper must accept the frozen eligibility as well as that date; its current create path rereads current `isActive` and would otherwise contradict the snapshot. Recompute response result/rank, never historic opt-in from current state.
4. **Historical data.** Recommend prospective execution receipts only, with no automatic backfill or global recalculation. Old ended quizzes remain read-only to the reconciler unless a separately reviewed recovery can establish their exact prior contribution. A historical repair would need its own private read-only impact check and approved data mutation.

These recommendations are design proposals, not decisions already made by an agent or reviewer. They are separate from the already approved close-race fix.

## Data protection, cost and unknowns

The proposed receipt uses existing participant/quiz/course references, execution identity and numerical accounting amounts only. Do not retain answers, names, emails, request bodies or auth tokens in it. It stays internal to authorized reward operations, with no new public API or analytics/export use. Participant deletion must cascade or otherwise remove its contribution link consistently with the existing reward records; referential and account-deletion tests are required.

The purpose is correctness and reversibility of rewards already collected, not new tracking. Keep its accessibility limited to the same backend roles, record only changes needed to explain totals, and include it in existing data inventory/export/deletion ownership. Existing transparency and purpose documentation needs a small review if execution receipts change the published account-data description. Accuracy and atomicity are the design's acceptance condition. Retention remains an explicit open decision: align with the existing reward record lifecycle and required recovery period; do not invent a new permanent archive or silently apply a retention period. No lawful-basis or retention ruling is made by this technical plan.

Expected cost is one contribution row per participating account per execution plus bounded updates, and any minimal idempotency receipt required by response processing. The two are different cardinalities; response receipts may dominate storage. Transaction/reconciliation time at large classes, sweep frequency and storage retention are unmeasured. Establish synthetic scale measurements and a bounded recovery policy before approval of live operation. No new provider or paid service is proposed. No real account, response or production aggregate belongs in public evidence.
