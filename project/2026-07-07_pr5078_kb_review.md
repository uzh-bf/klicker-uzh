# PR #5078 Review — KB Management Control Plane

- **PR**: [feat(kb): add knowledge base management control plane](https://github.com/uzh-bf/klicker-uzh/pull/5078) (`codex/kb-management-ui` → `v3-ai`)
- **Reviewed at**: 2026-07-07, HEAD `28c6427`
- **Reviewer**: Claude (multi-agent review: backend, frontend/UX, webhook security, infra/CI, bot triage), commissioned by Roland
- **Evidence**: code references below, local repro of CI failures, screenshots in `project/screenshots/kb-review/`

## TL;DR

The backend control plane (Prisma schema, GraphQL CRUD, signed webhooks) is solid and close to production quality. The frontend is a good-looking CRUD skeleton whose two most prominent surfaces — Settings and Knowledge Graph — are decorative demo data, and several visible buttons do nothing. Nothing consumes a KB at runtime yet (`apps/chat` is untouched), so the feature currently has no end-to-end user value; it is an internal-preview milestone, not a shippable feature. CI is red for reasons that are cheap to fix (one missing build step in a workflow, Sonar hotspot review).

**Recommendation**: merge as a preview milestone behind the existing owner-only access once the P0 items below are fixed; do not announce or expose to lecturers until at least the P1 items land.

## 2. UX and usefulness review

- The information architecture is genuinely good: catalog sidebar → resource table → inspector is the right shape for this domain, and the metrics header (resources / chunks / freshness) communicates system state at a glance ([01-catalog-overview.png](screenshots/kb-review/01-catalog-overview.png)).
- Loading, error, and empty states all exist ([04-*.png](screenshots/kb-review/)), destructive KB deletion asks for confirmation, and mutations surface success/error toasts.

- Honest no-op handling for reindex/internal-resource actions (toast "not connected in this shell yet") — better than pretending.

### Concrete UX defects

1. **CRITICAL — first-run dead end.** The empty state renders *instead of* the whole manager, including the sidebar that holds the only "create KB" button. A new user with zero KBs has no way to create one ([KnowledgeBaseManager.tsx:226-243](../packages/kb-management/src/KnowledgeBaseManager.tsx), empty-state screenshot [04-empty-state.png](screenshots/kb-review/04-empty-state.png) — no CTA). Fix: add a "Create knowledge base" button to the empty state (wire to `onCreateKnowledgeBase`).
2. **CRITICAL — snippet type mapping bug.** [kbMapping.ts:26](../apps/frontend-kb/src/lib/kbMapping.ts) maps `Snippet → 'text'` but the type registry uses id `'snippet'` (`packages/kb-management/src/utils.ts:12-41`). Real snippets get the fallback icon/label and fail the "Snippet" type filter. One-line fix + add a mapping unit test.
3. **MAJOR — bulk resource delete has no confirmation** while KB delete does (`window.confirm`). Irreversible, inconsistent.
4. **MAJOR — responsive breakage.** Inspector is `hidden xl:flex` ([KnowledgeBaseManager.tsx:371](../packages/kb-management/src/KnowledgeBaseManager.tsx)) — resource details are unreachable below 1280 px (13" laptops!). Below `lg` no mobile layout was designed; see broken [04-mobile-layout.png](screenshots/kb-review/04-mobile-layout.png).
5. **MAJOR — `window.prompt`/`window.confirm` for rename, linking, deletion.** Linking a chatbot requires pasting a raw CUID with no lookup, validation, or duplicate check. Not acceptable for lecturers; fine only for a developer preview.
6. **MAJOR — no i18n.** Entire package is hardcoded English; repo standard is next-intl DE/EN catalogs. `_app.tsx` wires `NextIntlClientProvider` but no component uses it.
7. **MAJOR — a11y.** `AddResourceDialog` has `role="dialog"`/`aria-modal` but no focus trap, no initial focus, no Escape handler (`AddResourceDialog.tsx:99-224`).
8. **MINOR — KB switch flashes the full-screen loading state** (`isLoading` includes `selectedKbQuery.loading`, index.tsx:154) — the whole manager unmounts on every selection.
9. **MINOR — freshness "change status" is hardcoded `unknown`** (kbMapping.ts:179-180) yet rendered as if live; subsite status hardcoded `Ready` (kbMapping.ts:157); dates formatted with hardcoded `en-GB` locale (kbMapping.ts:55).

### Usefulness verdict

**Nothing consumes a KB yet.** `apps/chat` has zero references to `KBChatbot`/collection IDs (verified by grep); linking a chatbot writes a row that no runtime reads. The webhook dispatchers fire into `KB_INGESTION_WEBHOOK_URL`/`KB_GRAPH_WEBHOOK_URL`, but no ingestion service exists. So today the deliverable is: a real control-plane data model + API, a polished demo UI, and a signed event contract for services yet to be built. That is a legitimate and well-executed milestone — but the PR should be framed (and gated) as such, because as a product feature it delivers no lecturer-visible value until ingestion + chat retrieval exist.

## 3. Backend quality (GraphQL / Prisma / webhooks)

### Webhook security — reviewed in depth, solid

- HMAC-SHA256 over `${timestamp}.${rawBody}`, timing-safe compare with length guard (`knowledgeWebhooks.ts:43-65`) — correct.
- Replay protection: timestamp tolerance (default 300 s) **plus** durable `eventId` dedupe via `KBWebhookInbox` — duplicate events return 200 idempotently.
- Raw-body handling registered per-route before any JSON parser (`apps/backend-docker/src/app.ts:198-216`) — avoids the classic body-parser-before-signature bug.
- Secrets/URLs only from env (`KB_*` vars), fail closed when missing, never logged. No SSRF vector (destinations are not user-controllable).

Remaining webhook gaps:

1. **MAJOR — GRAPH dispatch failures are silently dropped.** `dispatchResourceEvent` checks the INGESTION result and records `KBIngestionRun.status = FAILED` (`knowledge.ts:425-434`) but ignores the GRAPH dispatch result (`knowledge.ts:444`). A dead graph service is invisible. Fix: persist/log GRAPH failures symmetrically.
2. MINOR — missing-secret path returns 401 with "Webhook secret is not configured" (config disclosure; return generic "invalid signature").
3. MINOR — inbound `eventType` header is persisted without allow-list validation (`knowledgeWebhooks.ts:179-191,249`); unknown types silently no-op. Validate against the enum, 400 on unknown.
4. MINOR — no rate limiting on the public webhook endpoint (signature check fails fast, so low risk; defense-in-depth).
5. There is no webhook **retry** mechanism — a failed dispatch is recorded but never retried (deferred item #5 in `KB_BACKEND.md`; acceptable now, required before real ingestion).

### Backend findings (service/schema layer)

**Verified correct (worth knowing):** every KB query/mutation funnels through `assertOwnedKB`/`getOwnedKBOrThrow`/`getOwnedResourceOrThrow` scoped to `ctx.user.sub`; link mutations re-check ownership of the course/chatbot side too (`knowledge.ts:881-885,920-924`) — no cross-tenant path found. The one-enabled-KB-per-chatbot demote-then-upsert runs in a single atomic `$transaction` array. `migration.sql` matches `knowledge.prisma` exactly. Cascades are sensible (`KB → resources/runs/links` cascade; Klicker-object FKs `SetNull`).

Findings, by severity:

1. **MAJOR — non-transactional multi-step flows.** `updateKB` commits the KB row (`knowledge.ts:621`) and only afterwards dispatches per-resource graph webhooks (`knowledge.ts:647-667`); `deleteKB` soft-deletes resources + dispatches before flipping the KB status (`knowledge.ts:672-689`). A crash mid-flight leaves the external graph/ingestion state permanently inconsistent with no reconciliation path. Recommendation: outbox pattern — persist pending events in the same transaction, dispatch from a worker (fits the planned webhook-retry item).
2. **MAJOR — silent GRAPH dispatch drop** (same as §3 webhook finding #1; `knowledge.ts:443-449`).
3. MINOR — `createKBResource` runs recount + webhook dispatch via `Promise.all` (`knowledge.ts:695-736`); a throw after row creation surfaces an error although the resource exists.
4. MINOR — `kb.metrics_updated` inbound handler bumps `lastIndexedAt: new Date()` even when the payload carries no data (`knowledgeWebhooks.ts:395-410`).
5. MINOR — `getKB` declared `nullable: true` but the service always throws — dead null branch (`schema/query.ts:227-235`).
6. MINOR — changing a KB's `metadataProfile` never re-validates existing resources' metadata against the new profile (`knowledge.ts:600-604`) — integrity drift possible.
7. MINOR — `KB.settings` JSON exposes internal routing fields (`external.ingestionPipelineId`, `vectorNamespace`, `graphNamespace` — `packages/types/src/kb.ts:76-81`) to KB owners; split user-facing settings from internal plumbing.
8. Known/accepted — one-enabled-KB-per-chatbot has no DB-level partial unique index; any code path bypassing `linkKBChatbot` can violate the invariant silently (already in CLAUDE.md learnings).

### Backend test coverage gaps

Existing tests (`packages/graphql/test/knowledge.test.ts`) cover metadata/settings validation, webhook sign/verify round-trip, owner-only rejection for KB read/update/delete + chatbot linking, and dispatch failure paths. Missing:

- `linkKBCourse`/`unlinkKBCourse` cross-tenant rejection (only chatbot side tested).
- Owner-only rejection for resource CRUD and refresh-policy mutations.
- The full incoming-webhook **handler** (`handleKBIngestionWebhook`) with its `$transaction` writes — only the pure crypto helpers are unit-tested; replay via duplicate `eventId`, malformed JSON, missing secret are untested end-to-end.
- GRAPH dispatch failure path (which is why finding #2 went unnoticed).
- Express-level integration test that raw-body survives the real middleware pipeline.
