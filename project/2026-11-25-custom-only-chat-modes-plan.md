# Publish a chatbot with custom modes or Quizzer alone

## Approval summary

A lecturer can turn off Tutor, Explainer, Quizzer and Writing Coach, save a custom mode, preview it and submit the revision. After approval, a learner who opens the chatbot enters the custom mode directly. With two approved custom modes the learner can switch between them. A lecturer can also publish Quizzer as the sole mode with no knowledge base attached.

Allow incomplete drafts so the lecturer can edit the standard and custom sections in either order. At submission and again at approval, require the candidate revision to offer at least one conversational mode to participants. All four enabled standard modes and eligible custom modes qualify. With no KB, Quizzer provides general practice on a course-relevant topic or on material the learner supplies. With an authorized retrieval tool, it continues to use course sources. A published chatbot serves its last approved configuration throughout editing and review.

The first proof is a saved all-off configuration that survives reload and exposes its single approved custom mode in a learner turn. A second acceptance case takes a Quizzer-only chatbot from draft to a practice question and feedback with zero KB attachments. Delivery after approval is one verified draft PR into `v3-ai`, with browser evidence and configured reviews. This change uses the existing database columns, review flow and shared knowledge-base binding. Assigning different KBs to different modes is a separate follow-up. Merge, release and deployment are separate decisions.

**Stored settings.** The strict parser and persisted-data normalizer currently share the minimum-standard-mode check in `packages/util/src/chatbotStandardModeConfig.ts`. Keep the documented preview-only legacy behavior, with an empty saved custom list taking precedence over live managed modes. Participant layout, settings and POST must use live configuration. A new unpublished bot stays inaccessible to learners. A published bot keeps its approved modes during a pending, withdrawn or rejected revision. An explicitly disabled Tutor request must fail even if the server could select another mode. Keep the historical Tutor fallback for old messages whose mode was never recorded.

**Quizzer with and without sources.** When the effective Quizzer setting is on, offer it independently of KB attachment and allow it to satisfy the publication check. This also makes Quizzer visible on existing bots where it is already enabled, including by legacy default, but was hidden solely by the retrieval gate. Explicit opt-outs still hide it. Detaching the last KB leaves an enabled Quizzer available for general practice on the next turn.

Use the selected mode’s authorized retrieval configuration and actual discovered tools to distinguish these cases in both chat routes:

- With no applicable retrieval binding, omit the document query from the tool set and first-step choice. Adapt `mode-quizzer.hbs` through the existing compiler so it can ask about a topic the learner names, use pasted material, or ask one short question to establish a topic. Allow general subject knowledge within the course scope in ordinary chat and owner preview. For eLearning-origin threads, even after reopening in standalone chat, use only authorized supplied materials and ask for material if there is insufficient evidence. Cover both an absent page snapshot and the permitted retrieval outage. Ask one practice question, wait for the attempt and give specific feedback. Never imply access to a course document, invent citations or claim official exam coverage.
- With a safe, working retrieval binding, preserve the existing retrieval-first course-grounded behavior, citations and handling of insufficient evidence. An empty search result is still a grounded turn.
- A configured retrieval failure follows the existing error policy for that route, including the current eLearning page-context exception and mandatory rejection of scope violations. Keep disabled overrides, safe inheritance, scoped tokens and filtering of unsafe tools intact. Preview must intersect its document-query-only discovery restriction with the effective allowed tools, including supported aliases. Skip configurations that exclude retrieval. Exercise a concrete optional allow-list excluding document query and prove that preview cannot discover or call that tool. A failed discovery of a configured binding must not silently start general practice in a route that previously rejected it.

Keep `packages/graphql/src/lib/responseExampleContract.ts` consistent wherever it enumerates *available chat modes*. Preserve separate KB/source checks in capture, approval and edit-and-approve, including the safe Quizzer binding for all three operations. With a disabled binding and otherwise current evidence, Quizzer can be listed for chat while a stale capture and both approval paths still reject. Remove the KB-required hints from Manage summaries, EN/DE authoring and participant descriptions. Amend the Quizzer exception in ADR 0050 alongside ADR 0021 and the corresponding sections of the chat platform guide.

**Lecturer and reviewer experience.** Remove the last-standard toggle locks. Explain in the Modes and publication views how to resolve an incomplete draft. Reuse the existing setup blockers and localized mutation error handling. After reload, the setup summary and admin review must identify custom-only and Quizzer-only offerings accurately. Preserve pending-review and concurrent-edit locks. Reconcile the shared summary hunk with the separate [Writing Coach summary fix](https://github.com/uzh-bf/klicker-uzh/pull/7008) at delivery. ### Delivery, recovery and follow-up

The package uses `enhance/custom-only-chat-modes` targeting `v3-ai`. Approval starts implementation, focused fixes, local commits, ordinary task-branch push, a draft PR in the existing public repository, hosted checks, and the configured final review. Publish only source and reviewed synthetic evidence. The terminal condition is a verified draft with passing applicable CI, required review findings resolved, and browser evidence for the learner journey. A failing check triggers diagnosis, a scoped correction and rerunning affected evidence. If projection and preview disagree, hold the candidate and repair the earliest failing read path. If local browser fixtures fail, use the supported hosted Playwright path with the same synthetic scenario and preserve captures. Report any remaining missing evidence. A protected-branch or required human-review gate remains with the user.

A source revert is straightforward before activation. An old reader can bring other standard modes back for an approved custom-only or Quizzer-only bot and hide Quizzer when there is no KB. Any later rollout must update readers before enabling those writes, and account for existing opt-ins before rolling readers back. This plan requires no database migration, new dependency, extra model calls per quiz turn or live data access. Implementation review and CI consume their normal quotas.

Per-mode knowledge-base assignments remain a separate backlog item. An existing shared KB should continue to work in a custom-only bot. This package makes no change to attachment, retrieval scope, permissions or conversation isolation.
