# PRD lecturer-demo provisioning: two `klick` courses

Status: approved for the database-write boundary; activation, deployment, merge, and lecturer communication remain withheld.

## Problem

The `klick` account is the approved owner, but the requested demo must use one separate production course per chatbot. Existing similarly named courses are not owned by this account and must not be reused.

## Evidence

- The production account lookup resolves the unique shortname `klick` with administrator role.
- Current PRD rows contain an existing IuW course/chatbot, but no current RadioSurfVet binding. Neither existing IuW state nor another account's `testkurs`-like course is mutated by this package.
- The PRD shared endpoint is the existing `/mcp/klicker` route. The candidate tenant tools are `informatik_und_wirtschaft_video_expert` and `radiosurfvet_expert`.
- The approved derived bearer is mapped only in-process. No value enters a receipt or project artifact.

## Decision

Create two new active PIN courses under `klick`:

- `testkurs IuW`, with one new inactive IuW chatbot and one new inactive bearer-authenticated MCP server.
- `testkurs RadioSurfVet`, with one new inactive RadioSurfVet chatbot and one new inactive bearer-authenticated MCP server.

Each chatbot receives exactly two enabled strict MCP configurations, one Tutor and one Explainer, with the matching raw tool allowlist and `{ required: true, toolAlias: "doc_query" }`. Servers remain inactive. Each server is dedicated to its chatbot; no existing server is repointed.

Course dates are 2026-08-21 through 2027-08-31, with the group deadline at the end date. PINs are generated by the database/application defaults and are never written to the receipt.

## Risk controls

- Resolve the owner by shortname and require the expected administrator role.
- Use explicit UUIDs, exact names, and a values-free payload/state hash.
- Refuse existing IDs, duplicate owner/name targets, competing server names, partial rows, drift, active target servers, or unexpected bindings.
- Run dry-run first; apply only with a matching dry-run receipt.
- Apply all course, permission, disclaimer, chatbot, server, and binding creates in one Serializable transaction.
- Encrypt the approved bearer with the running app-key interface, verify decryptability in-process, and never print or persist the value.
- Do not activate either server, run W5e/reingestion, change cluster state, or contact lecturers.

## Slices

### S0 — write the approved two-course bundle

Route: main session; security and data-integrity coupling retained in the main session.

Do: add the ignored operational bundle and a dry-run-first Prisma Data script in the existing provisioner worktree. Reuse the canonical IuW prompt/disclaimer payload and the text-only RadioSurfVet contract; do not commit prompt bodies or corpus data.

Check: strict payload validation, repository script checks, and values-free dry-run against PRD.

Authority: local code/artifact edits and the explicitly approved PRD database writes are allowed; activation, deployment, merge, push, cluster changes, and lecturer communication are not.

Terminal: both new courses and their inactive chatbot/server/config rows read back exactly, with no unrelated row changes.

Pause: stop on owner mismatch, duplicate/partial state, endpoint drift, credential mapping failure, decryptability failure, or any transaction precondition change.

### S1 — verify the inactive production result

Route: main session.

Do: read back course ownership, generated PIN presence without printing it, chatbot/disclaimer ownership, inactive server state, endpoint, strict bindings, and unrelated-row counts. Record a values-free receipt in the coordination package.

Check: exact replay is a zero-write no-op; no activation or runtime request is made.
