# LTI failure logging

## Approval summary

Make ltijs route failures visible in ordinary service logs so a fresh failed launch can be diagnosed without collecting authentication material. User authority: the current Codex chat request, “so lets make sure we improve our logging to catch any such issues so i can test with her, check the logs, and fix”. This authorizes source implementation and ordinary draft delivery; it does not authorize merge, release publication, deployment, or an authentication fix.

Use the existing ExpressHttpHandler app middleware seam and ltijs Logger constructor option. A request-local AsyncLocalStorage context captures safe categories after the library parses the body. The logger records an allowlisted error category in that context; a response-finish observer emits one JSON failure record directly to stderr with the actual HTTP status. HTTP failures returned directly by application routes are logged too. The logger emits a minimal safe fallback immediately when parsing fails before the request context exists. Debug/warn retain existing gating. No exception is consumed and no response method is replaced. Record only fixed route and method categories, an allowlisted machine error code (unknown errors become a generic category), normalized Sec-Fetch-Site/Mode/Dest, recovered-state presence (missing/empty/present/invalid type), boolean state/id-token presence, and actual HTTP status where a completed request context is available. Never log raw errors, bodies, URLs, query strings, cookies, authorization headers, identifiers, token contents or hashes, IP addresses, or raw browser information. No request tracking identifier is added.

This is an internal observability change: no affected product primitive, validation policy, route, response, token, cookie, storage, or redirect contract changes. Existing application handoff rejection logs remain in place. Parser failures before request middleware receive an unconditional generic provider-error event without request metadata or inferred status; raw parser exception text is discarded. Requests that never reach the server remain a browser-side diagnostic limit. No upstream patches or response monkeypatching.

The terminal is a verified, independently reviewed draft PR into v3-ai. Production retesting requires a later explicitly approved release and deployment. No PR exists yet. Recovery is to correct the bounded logging implementation or report a concrete check/hook blocker, never bypass checks or weaken validation.
