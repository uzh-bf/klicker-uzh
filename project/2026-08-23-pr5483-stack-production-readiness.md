# Production readiness — PR #5481–#5483 stack (student-generated practice elements)

Date: 2026-08-23 · Auditor: Codex orchestrator (`$rs-production-readiness`) · Head evaluated: `7ecf61c569aee154e4494c760e9fb7a32c0d4394` over `origin/v3` at `d9e9b46a945c481476d2dcd97b2cf7349e49e5a2`

## Verdict

**Not ready.** Two candidate blockers survived wave one and could not be settled by wave-two verification, so they remain unverifiable blockers: (1) the repeatedly observed post-reload Chat hydration freeze that leaves the core conversation flow unusable, and (2) an unproven deployed `doc_query` chunk contract that, if mismatched, makes every approved card generation return nothing. The audit runtime never exposed working app routes (public URLs returned HTTP 404 across the whole audit window; internal probes on day two showed services started but Chat still unroutable), so neither blocker could be reproduced or refuted live. Everything else found is non-blocking: five lease/lifecycle integrity defects around generation settlement, a persistence-boundary gap that still accepts query-like metadata and unsanitized source URLs, silent partial-failure paths, several misleading error states in PWA and Chat, unbounded retrieval payload volume, full-table hydration lookups, and missing operator documentation. Current-head forge CI is otherwise fully green (all required checks pass; two aggregate status jobs were pending at last read), and the additive migration is backward-compatible with safe app-level rollback.

What would settle the unverifiable blockers:

1. **Hydration freeze** — restore the exact workspace's public routes without changing the branch head, then perform an authenticated thread create/reopen followed by hard reload, recording the final DOM state, console output, and chatbot API results. A passing interactive post-hydration snapshot (or proof the freeze belongs to the local environment, not feature code) clears it.
2. **`doc_query` chunk contract** — run one values-free staging probe against the configured Tutor-mode `doc_query` MCP server: `tools/list`, then one synthetic `tools/call`, asserting only that `sources` is non-empty and every source carries non-empty `chunks[]` whose entries contain one accepted ID field (`chunk_id`/`chunkId`/`id`) and one accepted text field (`content`/`text`/`excerpt`). Repository history records producer contracts (answer mode: no chunks; documents mode: chunks without stable IDs) that would fail the new adapter, so this probe must succeed before merge.
