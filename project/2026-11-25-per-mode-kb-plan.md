# Knowledge bases for custom chatbot modes

## Approval summary

A lecturer can give Case discussion a casebook and Exam practice a question bank. Both modes serve the same learners. Switching modes keeps the thread, visible messages and model conversation context. Each new search uses only the source selected for that turn. Earlier answers can still inform later answers. A mode may use an explicit KB even when the chatbot has no default.

Give the chatbot a list of linked KBs, at most one default, and each custom mode a reviewed choice of one link or “Use chatbot default.” Links are live. Selection changes reach learners on approval. An explicitly assigned source that becomes unavailable blocks the affected turn before model execution. A mode inheriting an empty default retains its existing KB-free behavior.

Approval starts one full-path source package on `enhance/per-mode-kb` into `v3-ai`. Deliver a draft PR with one migration, verified synthetic scenarios, browser screenshots, independent integrated review and applicable required CI. This uses normal development, review and CI resources. It stops at the verified draft. Marking ready, merge, releases, deployments, production data or backfills, and changes to other services require separate authority. GitHub's ready-only final AI review belongs to a later promotion. The main risk is an existing reader or writer treating every linked KB as available to every mode.

## Execution details

### Product contract

| Action | Observable result |
| --- | --- |
| Link an existing owned KB | Add it to the chatbot's source list. Adding another link leaves the default and existing assignments alone. The lecturer can choose a default or leave it empty. |
| Edit a custom mode | The picker shows linked KB names and the resolved default, including “no default.” Renaming a KB or mode preserves the association. Choosing inherit explicitly clears an override. |
| Save, submit, approve or reject | Owner preview reads the saved revision. Learners read only the approved revision. Review shows the source change. An invalid reference prevents submission or approval. Rejection leaves the published selection intact. |
| Change the default | Affects the next retrieval for inheriting modes. Identify affected modes before confirming. Existing standard-mode eligibility and legacy MCP restrictions continue to apply. |
| Unlink or delete | Show impacted draft and approved usages. Revocation takes effect for new retrieval and media reads. An explicit lost link stays visibly broken until reassigned. No automatic fallback or assignment resurrection on relink. Removing the default clears it. |
| Switch or reopen | Keep thread ID, transcript and authorized history. Resolve new tools and source per turn. An in-flight reply keeps its original mode. Reopening a historical attachment requires current access to its original source. No retroactive erasure of previously displayed text. |

The KB list grants eligibility for selection, never union search. Use the existing 32-link ceiling proposed in the [multi-KB plan](2026-09-08-chatbot-multiple-kb-follow-up-plan.md) as a transactionally enforced limit for enabled links. A KB link grants no new course or participant access. Keep KB identifiers and names for draft-only links out of learner bootstrap, graph pickers and tool descriptions.

### Test portfolio and first proof

Extend existing migration/GraphQL attachment, revision, scoped-token, graph, media, response-example and authoring Playwright suites at their existing seams. Use two synthetic KBs with distinct source IDs and an instrumented Doc Query transport that records actual signed claims and returns source-specific fixtures. Check provenance and attempted calls, independently of model wording. First prove the resolver and signed request on a custom-only chatbot with A, B and no default. Selecting A or B must send exactly that single KB; a missing explicit link must produce zero provider or document calls. Then exercise the same contract through preview, publication and learner chat.

### Delivery sequence

1. **Separate links from the default.** Extend `KBChatbot` with an explicit default flag. Generate one schema-aware Prisma migration; use manual SQL only for the conditional unique index, default-implies-enabled constraint and required data mapping. Backfill only enabled rows for undeleted, same-owner KBs as defaults. Leave disabled rows and their IDs intact, with default false. Disable stale links to soft-deleted KBs and disable their managed projections atomically. Abort the migration on inconsistent ownership or unclassifiable bindings instead of guessing ownership. Retain unique KB/chatbot pairs; replace the old partial unique index with uniqueness on chatbot ID where enabled AND default. Multiple enabled non-default links are valid. Rehearse against synthetic empty, enabled and historical disabled rows. Serialize link, default, detach and KB deletion operations with the established KB-before-chatbot locking order and consistent ordering for multiple KBs. Retries are idempotent; concurrent updates cannot produce two defaults or excess links.
2. **Keep existing clients compatible while enabling additive linking.** Give new clients explicit add-link and set/clear-default operations. The legacy attach operation continues to mean choose/replace the default; explicitly assigned secondary links survive. Preserve singleton-only semantics of deprecated singular read fields and expose the real default separately. Update both management screens, deletion impact, backlinks, provisioning CLI and reconciliation in `knowledge.ts` and `packages/prisma-data`. Default changes only reconcile default-derived MCP rows. Retain existing disabled exact overrides and required tool restrictions. Adding a link alone must never enable a tool. Verify existing standard/custom bots, attach from either surface, and stale writer retries.
3. **Make selection part of the reviewed mode.** Add an optional stable link ID to the existing typed mode JSON, input, GraphQL and generated operations. Omitted input preserves an existing selection under older clients; explicit clear means inherit. Validate against enabled, undeleted links owned by this chatbot and owner on save, submit and again during approval under consistent concurrency control. Compare draft and published snapshots by stable mode key. Show choices and unavailable sources in Manage and the review diff. Never replace a deleted reference with null during normalization. A detached then newly attached KB gets a fresh link identity. Inspect legacy disabled-row reuse so a stale ID cannot silently become valid again.
4. **Resolve one effective source at every read.** Extend the existing effective-mode and `mcpScope` paths. Obtain mode, configuration version and owning chatbot on the server; use one independently validated, currently enabled link to select retrieval. Derive the tool configuration and scalar signed claim from that same source. Keep server identity, allowed tool, required-binding, thread ownership and exact requested-scope checks. Preserve the legacy path for configurations without a new selection, including provisioned MCP-only configurations, without widening it to secondary links. Reject forged foreign, disabled, deleted, mismatched and stale links before discovery or model work. Recheck access at the next request and before issuing a new credential. Already-issued short-lived tokens keep their existing expiry contract. Keep admission/selection identical in standalone, embedded, eLearning and owner preview with their respective context restrictions. Use local synthetic token verification; no change to the external retrieval service is assumed.
5. **Close downstream reads and preserve conversation.** Apply selected-mode scope to graph hints, document images, video frames and response-example evidence/capture. Stamp new retrieved artifacts with original source and link provenance in existing structured message/evidence metadata, keyed to the producing mode; use existing source IDs when already present. Replay must verify the message belongs to the caller and the original source is still authorized for that mode; ambiguous legacy evidence is unavailable for replay. Preserve its transcript. Graph browsing is a separate learner surface: authorize its requested KB from sources actually available to the learner through approved, enabled modes with graph access, retaining ordinary graph policy; a draft-only or merely attached source is invisible. Cache keys and receipt verification must distinguish chatbot, effective source and relevant mode/revision. Preserve existing capture eligibility; exposing the picker must not newly qualify an unsupported capture mode. Recompute response-example eligibility against its source after reassignment. Do not strip earlier turns or reuse old tool results as fresh retrieval when changing modes.
6. **Prove the integrated journey and deliver.** In a synthetic browser fixture link A and B, leave default empty, publish two explicit modes, switch A → B → A in one learner thread and reload. Assert the same thread, preserved history supplied to the model, the selected mode on each message and the actual new retrieval scopes. Edit A to B in draft; verify preview changes while learners retain A, then approve and verify the transition. Exercise inherit, changing and removing a default, custom-only and KB-free Quizzer regressions; verify foreign/deleted links, revoked media, stale receipts, concurrent deletion/approval, attach limit and disabled/removed modes in focused tests. Check standalone and embedded entry points; verify the eLearning route without changing its signed context contract. Capture real lecturer, review and learner screens with synthetic data. Update ADR 0050, the schema invariant in `docs/data-and-migrations.md` and relevant management guidance. Run repo checks/build, inspect the scoped diff, run the configured integrated review for correctness, data scope, migration and compatibility, push normally and resolve applicable CI and findings on the draft.

### Compatibility, recovery and ownership

The main session owns migration, writer/reader coordination, history semantics, proof and delivery. This design supersedes the earlier plan’s combined-scope default and exclusion of per-mode assignment for this package. It retains live link management, the plural read contract and the limit of 32. Any future combined-search feature needs its own explicit policy. Keep plural writers unavailable until every consumer and provisioning writer supports them. Before activation, verify compatibility on an isolated database and exercise the existing external scope-token format locally. A deployment would need schema expansion and compatible readers/writers everywhere before enabling plural data. For rollout, quiesce legacy attachment mutations and provisioning jobs before migration and resume only on upgraded writers. Gate new plural mutations server-side until compatible readers and writers are confirmed. Document this sequence for separate deployment approval. Once several links exist, rolling back to the old singleton writer could disable them. Disable new edits and retain compatible readers while repairing forward; destructive collapse to a single link requires a separately approved data decision.

Start with focused failing fixtures and one bounded fix/rerun for a failed seam. If authorization or compatibility cannot be preserved by local source changes, hold new writes, document the observed blocker and return before expanding the package. A disposable local runtime or hosted synthetic CI provides browser verification. No broad cleanup, live migration or real course material is needed.

### Race and provenance rules

* Link, unlink, default, deletion, mode-save, submit and approval serialize their final validation/write against the same chatbot row. For multi-KB work, first acquire needed KB locks in sorted order, then the chatbot lock and re-read the live links and revision version. Preserve existing revision conflict responses. If revocation wins, an explicit assignment fails validation. If approval wins, later unlink immediately makes that published selection unavailable. An inherited selection publishes the instruction to follow the live default; approval never freezes its current KB.
* Resolve a request from one consistent snapshot at admission. Bind discovery, tools, graph hints and signing to the same link. If the link is revoked or reassigned before a new credential is issued, refuse that retrieval. Never resolve an in-flight request onto a different KB. A completed default change affects subsequent turns.
* Prior learner and assistant text remains available to the model across mode switches, including previously quoted material. A citation remains transcript text. Reading protected bytes or performing a new tool call requires current authorization. Use persisted assistant `ChatMessage.chatMode` and structured source parts in `ChatMessage.content` for the producing mode and original KB/link, plus equivalent claims in signed capture receipts. An old source may replay only where its original mode/KB and current entitlement can both be established. Never infer a missing origin from the currently selected mode or a newly attached link.
* Run a baseline fixture with only legacy MCP rows and zero managed links. Compare pre/post tool eligibility, authorized signed KB claim or preexisting refusal, plus behavior of a disabled exact override. Explicit selections must never fall through to this path. Unlink/deletion disables the managed projection in the same transaction so a revoked managed source cannot be rediscovered as legacy. Test this with unchanged unrelated MCP rows.
