# Gemini Embedding 2 for Klicker question revisions

## Approval summary

Give every recoverable question revision one versioned, multimodal vector in Klicker’s Azure PostgreSQL database. Generate it asynchronously so authors can save and lecturers can sample and rate questions independently of model latency. A first consumer should be able to retrieve the vector for an exact revision subject to the same question permissions. Search, classifier training and changes to the [lecturer sampler](PLAN-question-pool-label-preview.md#sampling-and-validation) are separate work.

**Status: planned; Azure inference route unverified.** The requested model ID is `gemini-embedding-2`. Google documents a hosted API. Microsoft’s public embedding catalog does not establish an Azure-hosted EU inference route for this exact model. Running a Hatchet worker on Azure and sending question contents to Google would change the processor. The default plan requires Azure-side EU processing for inference and storage. An operator must verify the serving model, region, processing boundary, terms, quota and price before any real content leaves the worker. Substituting EmbeddingGemma 2 would create a different vector space.

This is a design for a conditional implementation batch. Start with the route decision below. Implementation, paid inference, production migrations and backfill need their own authority. [Google model contract](https://ai.google.dev/gemini-api/docs/embeddings) · [Microsoft Foundry embedding catalog](https://ai.azure.com/catalog/models?task=embeddings)

## Route decision and first proof

1. Check the intended Azure subscription and EU region for an exact deployable model SKU or a supported licensed self-hosted distribution. Record evidence of where the input is processed, the serving model and version, permitted media, quota and unit price. Catalog presence, an Azure-hosted gateway or a working Google API key alone cannot establish the processing boundary. If the exact model remains unavailable, close the feasibility batch with a documented no-go. Leave the engineering slices unstarted until the owner approves a different processor or model. A stub cannot qualify the serving route.
2. Once the route and a finite spend cap are approved, send one synthetic German text question and one synthetic English question with a figure through the intended route. Build **one multipart content object per question**. Request 768 dimensions, verify exactly one finite, nonzero vector of that length per item and L2-normalize before storage. Compare a paraphrase and a changed figure to catch dropped inputs. Record observed request units, latency and cost, including attempts. Preserve the model/deployment revision or an operator-controlled generation identifier if the service can change behind an alias.

## Revision identity and storage

- Use the question’s element ID and integer version. Extend the existing question-type projection across SC, MC, KPRIM, numerical, free-text, selection and case-study formats. Capture participant-visible stems, typed options or prompts, case criteria and referenced media in authored order. Flashcards need a front/prompt projection; content-only elements fall outside the question denominator. Use frozen answer-collection text where a question references a collection. Exclude correctness flags, solutions, explanations, lecturer labels, course outcomes and participant data. Resolve authorized media references to content bytes or immutable versions. Include those digests in the fingerprint and preserve accessible alt text. Report unavailable media, conflicting snapshots and over-limit inputs explicitly rather than embedding a partial question as complete.
- `Element.version` identifies the current mutable record. `ElementInstance.elementData` can provide historical snapshots for revisions actually used. Establish one canonical projection per revision and fingerprint it with its serialization version. First trace create, edit, import, copy and answer-collection updates to the write transactions and verify which changes advance the revision. Treat two different authoritative projections for one ID and version as a conflict requiring source reconciliation. Capture immutable projection inputs or references in the same transaction as each new revision, including imports, duplicates and edits; queue work only after commit. If mutable media or answer collections can change independently, pin their content at capture. For an existing snapshot, require evidence that each dependency matches its value at the time of the revision. A mutable URL or collection ID alone is insufficient. Record a historical gap if that evidence is missing. A job for an old revision must never read today’s wording for that ID.
- Use one related Prisma record per element ID, element version and embedding generation, with a unique database constraint. Record projection fingerprint, media identity, model/version, dimension, generation status, attempts and completion time. Keep one authoritative ready vector per revision for the active generation. Validate PostgreSQL vector extension availability on the Azure target before selecting column DDL; the proposed storage is `vector(768)`. Generate one additive migration through the repo’s schema-aware workflow. Define the generation signature over the serving model revision, task instruction, ordered multipart encoding, media policy, dimension and normalization. Defer approximate vector indexes until a concrete query and scale test justify one.
- Apply current element permissions before any vector read or similarity result, including shared/copied elements. A historical vector read additionally requires access to the exact historical content through an existing authorized revision or instance. Deny the read if that check cannot be made. A copy inherits its own access checks. Treat vectors and pending projection data as private derivatives. Exclude deleted items from reads immediately and propagate deletion/purge under the parent’s retention rules. Store IDs and error classes in job telemetry; suppress question payloads, media access tokens and vectors.

## Worker, backfill and acceptance

1. Reuse the general Hatchet worker and its workflow registry. A durable pending record and a reconciliation pass cover the interval between save and dispatch. Send only the immutable revision identity in the job. Claim work atomically; use bounded retries with backoff for transient failures. Commit a result only if generation and fingerprint still match. Replays converge on one ready row; an old worker cannot overwrite a new generation. Track ambiguous provider timeouts against the spend cap even when retries are safe for database state.
2. Inventory current questions plus distinct recoverable historical revisions. Deduplicate repeated instance snapshots by exact revision and fingerprint. Report conflicts, absent archives and missing dependencies separately. Never reconstruct an unavailable revision from its successor. Use a resumable keyset cursor, bounded concurrency and a catch-up pass for edits during the scan. Before a real backfill, report coverage by type, projected units, cost range, a hard cap including retries and the stop switch. An additive model upgrade builds a separate generation; switch reads only after validation. Roll back reads to the preceding generation and pause dispatch if needed.
3. Verify with synthetic fixtures: two quick edits completed in reverse order, concurrent duplicate deliveries, failed media reads, permission revocation, deletion during processing and interrupted backfill. Reconcile ready, pending, failed and unrecoverable revisions to the inventory; verify exactly one active vector per successful revision. Include rendered text with media and a selection/case-study fixture with historical collection values. Confirm that a disabled worker leaves authoring and lecturer sampling functional.
4. End the implementation batch at a verified synthetic end-to-end run on the approved route, a reviewed migration and a dry-run inventory design. Deployment and any real backfill are separate decisions with an environment, named scope, budget and acceptance counts. An operational backfill completes only when every inventoried revision has a verified vector or an explicit reconciled exception.

## Progress

The sampler decision is recorded independently. Public provider documentation establishes the exact Google model contract. Azure-native EU inference for that model is the outstanding feasibility question. No provider, schema change or live processing has been activated by this plan.
