# EmbeddingGemma 2 for Klicker question revisions

## Approval summary

Give every recoverable question revision one versioned, multimodal vector in Klicker’s Azure PostgreSQL database. Generate it asynchronously so authors can save and lecturers can sample and rate questions independently of model latency. The first product use is finding similar questions from a saved question in the lecturer pool. The storage batch proves that lookup with synthetic revisions. The lecturer interface ships as a subsequent change. The [blind-rating sampler](PLAN-question-pool-label-preview.md#sampling-and-validation) runs independently.

**Execution target.** Run the locally tested `google/embeddinggemma-2` text-and-vision encoder on the planned shared Azure Spot GPU pool in the approved EU region. Keep question content, inference and vector storage within that boundary. Package pinned weights and processor assets for offline loading. The first Azure milestone is a synthetic parity and throughput check on the actual pool. Implementation, infrastructure changes, paid runs and production backfill require separate authority. [EmbeddingGemma 2 model card](https://huggingface.co/google/embeddinggemma-2)

## Product uses and runtime latency

1. **Find similar questions from a saved question.** Help lecturers reuse an existing item, find its German or English counterpart, or inspect possible duplicates before adding another variant. Read the selected revision’s stored vector and rank other current, permitted questions within the lecturer’s active pool filters by cosine similarity in PostgreSQL. Exclude the source element and other revisions of that element. Apply access and scope constraints before returning the top results. Preserve source lineage for family identity. A high similarity score can warrant inspection even when two questions test different skills. When a new revision is pending, show that state and let the lecturer continue working. Never serve its previous revision’s vector as current.
2. **Support question generation.** From a saved seed question, retrieve related revisions in the lecturer’s authorized course and generation source set. Pass a small, diverse set of examples within the generation job’s existing content and processor permissions. EmbeddingGemma retrieves examples; the generation model writes the question. For a brief without a seed, encode the brief once in the asynchronous generation job. After drafting, batch-encode candidates and retrieve close matches from the allowed pool and the same draft batch. Flag possible repetitions for review, retaining matches that test a different operation on the same topic. Keep held-out exam questions outside the generation context. A separately authorized evaluation can check overlap without returning held-out content to the generator. Persist a revision vector when the draft becomes a saved question. Verify with the exam-generation project’s synthetic German/English pairs, including paraphrases and same-topic questions that require different answers.
3. **Analyze pools in batch.** Reuse persisted vectors to group related items for a coverage review, surface possible duplicates after an import and retrieve candidates for a held-out exam overlap check. Validate candidates with the lecturer or exam review process before changing a family or excluding an exam question. Evaluate a difficulty or Bloom classifier offline against held-out labels before giving its predictions a product role.
4. **Add free-text semantic search only after item-to-item retrieval proves useful.** A newly typed query needs its own compatible vector. Keep the pool’s existing text results, 300 ms debounce, immediate Enter and immediate clearing. For a submitted query, display text results first. Encode once using a warm EU CPU worker with the pinned EmbeddingGemma generation and a tested text-query projection. Cache query vectors briefly by access scope, normalized text and generation; recheck permissions on every search. Cancel or ignore superseded requests. Show additional semantic matches only for the current query within its deadline. On a timeout or unavailable encoder, retain the text results and release the request. Keep raw queries out of logs. If a warm route cannot meet the budget, ship item-to-item lookup and keep free-text search lexical.

**Proposed acceptance targets.** Measure item-to-item lookup from click to results on representative pool sizes and restrictive permission filters. Start with p95 at or below 300 ms and zero inference requests. Begin with a scoped exact scan and add an index only if measurements require it. For free text, propose a one-second end-to-end deadline from submission for semantic matches. Measure cold cache, warm cache, concurrent requests and worker unavailability separately. Compare top-five relevance and redundant hits against ordinary text search using lecturer judgments on German, English and figure-dependent items. These targets guide the first benchmark; current performance is unmeasured.

## Spot GPU batch generation

Use Hatchet to dispatch background embedding jobs to GPU workers on the shared Azure Spot pool. Keep the encoder loaded across batches. Group compatible inputs by text length and image budget, with one question per example and one validated output per revision. Bound batch size by measured GPU memory. Give generation jobs and new revisions priority over bulk backfill; cap backfill concurrency so it yields capacity to other workloads. Use separate queues for embedding and generative inference so the appropriate model worker claims each job. A lost Spot node releases its work through lease expiry. Commit completed revisions independently and resume unfinished work from the durable queue.

Measure throughput and cost per thousand ready revisions, GPU memory, queue age and time from save to vector readiness under mixed load. Stored-vector lookups continue when the pool scales to zero. Do not make interactive requests wait for a GPU worker to start.

## First proof on the Azure Spot pool

1. Once the pool is available and the run has a finite spend cap, record its region, GPU SKU, quota, worker image digest and pinned model and processor revisions. Load the published text-and-vision weights with audio disabled. Use the local FP32 CPU encoder as the reference for the 768-dimensional normalized output. Qualify GPU precision against that reference before backfill. [EmbeddingGemma 2 developer guide](https://developers.googleblog.com/en/embeddinggemma-2-the-developer-guide/)
2. On the same synthetic bilingual question pairs and chart probes, compare CPU and GPU nearest-neighbor rankings. Check that both text and figure changes affect retrieval and that batching yields one finite unit vector per item in input order. Increase batch size against representative text and image lengths, record peak memory and cost including replays, then interrupt a batch and verify complete recovery without duplicate ready rows. Record parity tolerances before running the comparison. Pool provisioning or capacity delays hold this Azure check open.

## Revision identity and storage

- Use the question’s element ID and integer version. Extend the existing question-type projection across SC, MC, KPRIM, numerical, free-text, selection and case-study formats. Capture participant-visible stems, typed options or prompts, case criteria and referenced media in authored order. Flashcards need a front/prompt projection; content-only elements fall outside the question denominator. Use frozen answer-collection text where a question references a collection. Exclude correctness flags, solutions, explanations, lecturer labels, course outcomes and participant data. Resolve authorized media references to content bytes or immutable versions. Include those digests in the fingerprint and preserve accessible alt text. Report unavailable media, conflicting snapshots and over-limit inputs explicitly rather than embedding a partial question as complete.
- `Element.version` identifies the current mutable record. `ElementInstance.elementData` can provide historical snapshots for revisions actually used. Establish one canonical projection per revision and fingerprint it with its serialization version. First trace create, edit, import, copy and answer-collection updates to the write transactions and verify which changes advance the revision. Treat two different authoritative projections for one ID and version as a conflict requiring source reconciliation. Capture immutable projection inputs or references in the same transaction as each new revision, including imports, duplicates and edits; queue work only after commit. If mutable media or answer collections can change independently, pin their content at capture. For an existing snapshot, require evidence that each dependency matches its value at the time of the revision. A mutable URL or collection ID alone is insufficient. Record a historical gap if that evidence is missing. A job for an old revision must never read today’s wording for that ID.
- Use one related Prisma record per element ID, element version and embedding generation, with a unique database constraint. Record projection fingerprint, media identity, model/version, dimension, generation status, attempts and completion time. Keep one authoritative ready vector per revision for the active generation. Validate PostgreSQL vector extension availability on the Azure target before selecting column DDL; the proposed storage is `vector(768)`. Generate one additive migration through the repo’s schema-aware workflow. Define the generation signature over the serving model revision, task instruction, model input formatting and precision, media policy, dimension and normalization. Defer approximate vector indexes until a concrete query and scale test justify one.
- Apply current element permissions before any vector read or similarity result, including shared/copied elements. A historical vector read additionally requires access to the exact historical content through an existing authorized revision or instance. Deny the read if that check cannot be made. A copy inherits its own access checks. Treat vectors and pending projection data as private derivatives. Exclude deleted items from reads immediately and propagate deletion/purge under the parent’s retention rules. Store IDs and error classes in job telemetry; suppress question payloads, media access tokens and vectors.

## Worker, backfill and acceptance

1. Reuse the existing Hatchet workflow registry for orchestration and dispatch inference to the Spot embedding workers. A durable pending record and a reconciliation pass cover the interval between save and dispatch. Send only the immutable revision identity in the job. Claim work atomically; use bounded retries with backoff for transient failures. Commit a result only if generation and fingerprint still match. Replays converge on one ready row; an old worker cannot overwrite a new generation. Include interrupted GPU batches and retries in compute accounting.
2. Inventory current questions plus distinct recoverable historical revisions. Deduplicate repeated instance snapshots by exact revision and fingerprint. Report conflicts, absent archives and missing dependencies separately. Never reconstruct an unavailable revision from its successor. Use a resumable keyset cursor, bounded concurrency and a catch-up pass for edits during the scan. Before a real backfill, report coverage by type, projected units, cost range, a hard cap including retries and the stop switch. An additive model upgrade builds a separate generation; switch reads only after validation. Roll back reads to the preceding generation and pause dispatch if needed.
3. Verify with synthetic fixtures: two quick edits completed in reverse order, concurrent duplicate deliveries, failed media reads, permission revocation, deletion during processing and interrupted backfill. Reconcile ready, pending, failed and unrecoverable revisions to the inventory; verify exactly one active vector per successful revision. Include rendered text with media and a selection/case-study fixture with historical collection values. With the worker stopped, verify that authoring and lecturer sampling work, a ready revision returns scoped neighbors without inference, and a pending revision reports its state.
4. End the implementation batch at a verified synthetic end-to-end run on the planned Azure pool, a reviewed migration and a dry-run inventory design. Deployment and any real backfill are separate decisions with an environment, named scope, budget and acceptance counts. An operational backfill completes only when every inventoried revision has a verified vector or an explicit reconciled exception.

## Progress

EmbeddingGemma 2 has run locally on CPU with text and figures. The plan adopts it for question-pool retrieval and generation support. Azure GPU parity, eviction recovery, throughput and cost remain to be measured when the shared pool is ready. The lecturer sampler retains its deterministic tag-and-wording rule.
