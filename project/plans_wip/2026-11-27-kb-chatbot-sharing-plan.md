# Lecturer sharing for knowledge bases and chatbots

## Approval summary

A lecturer can share a knowledge base (KB) or a chatbot with another lecturer or a user group through Manage. KB Read includes using the KB in the recipient’s bots. An editor of someone else’s bot may attach a KB when both the editor and the bot owner can read it. Students continue to access the published bot through its existing participation rules.

A bot’s continued use of a KB depends on its owner’s current access. Losing the last grant makes the selected KB unavailable for new retrieval. Keeping any qualifying grant keeps it usable. Prior messages remain readable under existing thread permissions. Teaching teams can recover by restoring access, replacing the selection, or removing it. The settings screen explains the unavailable selection without disclosing sources.

Approve one executable batch of three dependent draft PRs targeting `v3-ai`, where the KB model and runtime live. The batch covers implementation, synthetic verification, independent review, ordinary task-branch pushes and draft delivery through required CI. Merging, release, deployment, live data changes and paid model experiments require separate authority. This draft PR presents the plan for review. Implementation awaits approval.

## Permission contract

| Level | Knowledge base | Chatbot |
| --- | --- | --- |
| Read | List and inspect the shared KB and its source material. Select it in an eligible bot. | List and inspect lecturer-facing setup. |
| Write | Maintain ordinary source material, including normal ingestion associated with an edit. | Edit lecturer-authorable setup and its saved draft. Attach, replace or remove the KB selection. |
| Admin | Write plus grant, change and revoke lecturer and group access. | Write plus grant, change and revoke lecturer and group access. |
| Owner | Existing lifecycle, deletion and separately gated operations. | Existing lifecycle, deletion and publication submission. |

KB Read exposes protected material through authenticated, server-mediated reads. Keep Blob credentials, read capabilities usable outside the app, and the ingestion source gateway out of shared responses. Preserve external public links. Only owners retain deletion and existing owner lifecycle powers.

Keep existing account and feature eligibility, funding, operations approvals, paid graph builds, generation, private preview and conversation access at their present boundaries. The shared setup projection must exclude participant threads, private review data, credentials, and privileged integration configuration. Extend the existing single-owner model without introducing transfer for KBs or bots in this batch. Transfer has additional storage, course and billing consequences. No Execute level applies. Sharing a course, bot or KB creates no lecturer grant on the other objects. A participant can use the approved bot without acquiring a lecturer KB grant.

Reuse direct and group grants, their effective highest level, existing group membership changes and the shared role-change and revocation services. Reuse the Share action, object-sharing modal, role matrix, default Read, shortname/email and group controls, access table, badges and removal confirmation. Add the two object types to those components and supply the relevant actions in German and English. Introduce the KB Read row explaining chatbot reuse in layer 2, when recipients can first select a shared KB. Use the existing revocation dialog for KBs. For an individual grant, preview whether Read would survive through another grant as of the check; the committed effective permission remains authoritative. For a group grant, explain that each member’s other grants still apply. Explain that affected bots lose new retrieval and previously delivered answers remain readable. Keep other groups’ membership and foreign bot identities private. Expose only supported actions, including in direct API calls. Keep catalog listings, access requests, propagation and ownership transfer outside the new object types’ available actions.

## Revocation and recovery

| Event | Observable result |
| --- | --- |
| Owner loses one direct or group grant but still has at least Read | Bot continues to use the selected KB. The lecturer’s edit controls reflect the effective level. |
| Owner loses the final Read grant, directly or by group change | New protected reads and retrieval stop once revocation commits. Manage reports the selection unavailable. Other bots whose owners retain access continue working. |
| Only the attaching editor loses KB access, or loses their chatbot role | The editor loses the corresponding controls. The bot continues to use its owner’s access. |
| Owner regains Read | The same selected, available KB becomes usable again. An explicitly detached or replaced KB stays detached. A deleted KB follows normal deletion cleanup. |
| Access changes during an open page, active chat, queued job or upload | Recheck before the next protected server operation. Preserve already delivered content and work already accepted within existing service authority. Recheck at publication of new privileged results and confirmation of pending writes as applicable. |

Use current committed grants and group membership for authorization if derived-row updates can lag. Demonstrate the actual transaction or invalidation guarantees before relying on cached permissions. Distinguish prior message text from a newly issued citation download or fresh asset URL. Already delivered bytes and independently accessible public URLs cannot be recalled. Doc Query scope tokens last five minutes. Before publishing cross-owner attachment, require proof of a fresh effective-access decision on each protected tool dispatch, including a second tool call after revocation on an already-open session. Gate ordinary and graph-assisted calls plus retries, and exercise retained tool instances through a synthetic provider call counter. A short token lifetime alone does not satisfy this guarantee. Verify which components can independently initiate a read; the lecturer/student MCP authentication examples in the testing guide do not establish the external Doc Query verifier’s behavior. If a consumer outside this repository can independently authorize new reads after revocation, record the specific boundary and bring the smallest integration decision back before claiming immediate enforcement.

### Reads outside chat tool dispatch

Cover these two paths in layer 2 before enabling cross-owner attachment.

- **Participant knowledge map.** The knowledge-graph route serves overview, search, neighbors and concept mentions directly. In `apps/chat/src/lib/server/knowledgeGraph.ts`, the reader resolves the published graph before reading and checks it again before returning the result. Include the bot owner's effective KB Read in both decisions through `getPublishedKnowledgeGraphForChatbot`. Extend `apps/chat/test/knowledge-graph-route.test.ts` with a participant who still belongs to the course: after the owner loses their last grant, a fresh map request returns no graph data. Also cover revocation between the initial read and the final check.
- **Response-example capture.** An owner can present a receipt from an earlier preview to save an example. `packages/graphql/src/services/responseExamples.ts` checks the receipt and current sources; `loadCurrentResponseExampleResources` in `packages/util/src/responseExampleEligibility.ts` selects sources through enabled bindings. Require current owner Read when evaluating those sources. In `packages/graphql/test/responseExamples.test.ts`, issue a receipt while the owner has access, revoke the final grant, then verify capture rejects it as stale and writes no candidate or evidence references. An overlapping grant that preserves Read should still allow an otherwise valid receipt. Keep capture and review owner-only.

### Participant experience and history

If one KB in a mode’s required multi-KB scope becomes unavailable, stop that retrieval operation and show the existing localized unavailable state without identifying the KB. Quietly narrowing the configured scope would change the grounding promised for that mode. An independent mode can continue under its existing rules. Previously delivered text remains visible. A fresh protected citation, image or frame request shows the unavailable placeholder if denied. Check follow-up prompt assembly as well as display: retain conversation text the participant already received and exclude retained internal tool payloads from an inaccessible KB when constructing a new model request. If no such payload is replayed today, verify that behavior with the synthetic fixture.

A bot manager who still has KB Read can identify the selection and arrange for the bot owner to regain Read. Other managers see a generic explanation and can replace or remove the selection if they have Write. Losing a bot owner leaves the existing owner-only lifecycle limitation; this batch introduces no transfer workflow.
