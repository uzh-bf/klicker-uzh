# Element Import/Export Packages

**Import/export duplicate detection is advisory, not authoritative.** The backend computes internal fingerprints for elements and answer collections to show duplicate warnings, but imports still create the selected elements and their required package dependencies. Users decide by selecting or deselecting preview rows.

## Package format

Element packages are strict ZIP archives produced and parsed by `packages/graphql/src/lib/zip.ts:createZip` and `packages/graphql/src/lib/zip.ts:parseZip`. The parser accepts only root `manifest.json`, declared element JSON files, declared answer collection JSON files, and declared media files. JSON files must contain valid UTF-8; malformed byte sequences are rejected rather than replaced with mutated authored text. The parser rejects directory entries, macOS metadata, non-canonical or duplicate paths, unsupported compression methods or flags, data descriptors, inconsistent EOCD/central/local metadata, overlapping or incomplete local records, trailing compressed/archive bytes, CRC mismatches, unexpected files, and oversized compressed or uncompressed payloads.

The package manifest type is `klicker-element-package` and the current version is `3`, configured in `packages/graphql/src/lib/importExportPackageConfig.ts:IMPORT_EXPORT_PACKAGE_VERSION`. Its strict schemas and canonical paths live in `packages/graphql/src/lib/importExportPackageContract.ts`. A package contains 1–100 elements, at most 50 answer collections, at most 2,000 entries per collection and 5,000 entries overall, at most 5,000 selected answer-entry relations across all elements, at most 100 non-empty media files, at most 200 closed-enum warnings, and the configured JSON/media/archive byte limits. Raw warning arrays are bounded before duplicate warning codes are collapsed; import still discards package-authored warnings and derives its own warning set. Each raw element-options payload is measured against its byte budget before domain canonicalization, so an oversized malformed case study cannot trigger expensive nested validation before rejection.

Upload capabilities, local-download capabilities, and final import tokens share the strict framing, bounded base64url decoding, canonical-JSON check, timing-safe HMAC comparison, and explicit signing-context separation in `packages/graphql/src/lib/strictSignedCanonicalPayload.ts`. Each caller keeps its own payload schema, purpose, ownership, and expiry policy; the shared codec must not make one token class valid in another context.

Version 3 does not transport source element status or answer-collection version. Supplying either field is invalid. Every imported element starts in `REVIEW`, and every imported answer collection starts at version `1`, regardless of source state. This deliberately models import as a new authored copy rather than an exact workflow/version clone.

Personal element tags are intentionally outside the portable package contract. Exported archives never contain tags, imported elements start untagged, and a package that adds undeclared tag fields is rejected by the strict schema. Normal tag management for authored elements is unchanged.

## Canonical didactic payload

Every package element is validated against `packages/graphql/src/lib/elementDomain.ts:canonicalizeElementDomain`, the same neutral option boundary used by normal authoring. The package schema is a strict discriminated union across `SC`, `MC`, `KPRIM`, `FREE_TEXT`, `NUMERICAL`, `CONTENT`, `FLASHCARD`, `SELECTION`, and `CASE_STUDY`; unknown option fields and type-inapplicable answer-collection relations are rejected. Cross-reference validation then proves that selection/case-study entry refs are unique members of the declared linked collection.

Final export and export preview load the complete scoring/relation payload and validate it before serialization. A legacy source that the current importer would reject produces the stable `ELEMENT_NOT_PORTABLE` outcome rather than an archive that cannot be re-imported. Free-text solution whitespace is canonicalized, but its Unicode normalization form is preserved because the current grader distinguishes those encodings; import therefore cannot silently change a valid solution's scoring semantics. The full per-type invariant and grading rules are documented in [Domain Model](./domain-model.md#canonical-element-domain).

Normal authoring keeps that strict boundary for creations and explicit option edits. A partial edit that changes only shared fields such as name, status, content, or tags preserves existing legacy options and answer-collection relations instead of forcing an unrelated migration through the import/export canonicalizer. Such an element remains non-portable until its options are explicitly corrected.

The package carries didactic content, solutions, feedback, point settings, and required answer-pool data. It does **not** carry psychometric observations: participant responses, item statistics, difficulty, discrimination, reliability, validity, calibration, activity instances, analytics, and grading history remain outside the contract. Imported elements are uncalibrated copies in `REVIEW`, not psychometrically equivalent items. The Manage UI discloses this exclusion before both export and import so an archive is not mistaken for a calibrated or historically equivalent item.

Error and warning transport uses a closed GraphQL enum with localized recovery behavior; packages cannot supply UI messages. See [Import/Export Error Contract](./import-export-error-contract.md).

## Manage review and commit workflow

`apps/frontend-manage/src/lib/elementImportWorkflow.ts:ElementImportWorkflowState` makes upload a tested `idle → uploading → validating → reviewing → importing → success/error` reducer workflow. `apps/frontend-manage/src/components/elements/manipulation/useElementImportWorkflow.ts:useElementImportWorkflow` owns the abort controller and monotonically increasing request generation: closing during upload or validation aborts the request, and a late completion from an invalidated generation cannot reopen or replace the current review. Drops and replacements stay disabled through upload, validation, and import commit. `apps/frontend-manage/src/components/elements/manipulation/UploadModal.tsx:UploadModal` is the modal shell and selects the phase view from that hook state.

The final import mutation is the commit boundary. `useElementImportWorkflow` owns that mutation, error translation, and the subsequent list refresh; `UploadModal` removes close/cancel actions and disables Escape only while the mutation can still be committing. During that phase the hook also registers a native unload prompt and restores/declines Pages Router history pops, so refresh, tab/window close, and browser Back cannot silently abandon a request whose durable outcome is not yet known. A mutation failure removes those guards and returns the same selection to review with a focused inline error. Mutation success moves irreversibly to the success state before refreshing the element list, at which point navigation, close/cancel, and Escape become available again. Closing invalidates the refresh generation before unmounting, so its late result cannot show a stale warning, dispatch into the closed workflow, or close another modal. A failed post-commit refresh observed while still open therefore shows localized committed-success and reload guidance with no import action, not a retryable import failure that could invite a duplicate commit. `ImportedElementsOverviewTable` owns selection and presentation only.

The review is driven by the current Formik selection rather than package totals. `ImportedElementsOverviewTable` recomputes the selected duplicate count and required answer collections after every toggle and provides select-all, select-none, and exclude-existing-match actions. `apps/frontend-manage/src/components/elements/manipulation/PackageAnswerCollectionOverview.tsx:PackageAnswerCollectionOverview` shows only collections needed by the current selection and mounts their complete entry lists only when the lecturer expands them. The didactic answer pool follows the same lazy-mount rule, so a valid 2,000-entry closed pool does not create hidden list nodes. One semantic responsive list is shared across breakpoints; there are no separate desktop/mobile selection trees that can drift apart.

The validation response transports each full answer pool exactly once under top-level `answerCollections`. Per-element preview rows carry only `answerCollectionRef` and selected `answerCollectionItemIds`; `packages/graphql/src/schema/elementImportExport.ts:ElementImportPackagePreviewElement` does not expose repeated entry/value arrays. Its `options` field is the nine-member `ElementImportPackagePreviewOptions` union defined in `packages/graphql/src/schema/elementImportPreviewOptions.ts`, never the `Json` scalar. Generated clients therefore discriminate SC, MC, KPRIM, numerical, free-text, content, flashcard, selection, and case-study payloads by `__typename`; choice correctness remains nullable when no sample solution exists, and numerical placeholders—including Unicode text—are transported as authored. `apps/frontend-manage/src/lib/elementImportPreview.ts:createElementImportReviewModel` exhaustively converts that union and derives each preview's complete pool from the top-level ref map without `any` or JSON casts. This prevents a valid 100-element package sharing one 2,000-entry collection from multiplying the same authored values across the GraphQL response.

The server-side canonical domain keeps the same discrimination through `CanonicalOptionsByElementType` and `CanonicalElementDomain<Type, Id>`. Package schemas therefore preserve each literal element type's canonical option shape through dependency validation, immutable execution plans, preview construction, and the Pothos preview union. Case-study package refs are converted to database item IDs through typed structures rather than `any` or record casts. Runtime canonicalization remains the trust boundary for all externally supplied JSON.

`packages/graphql/src/services/elementImportPreviewModel.ts` builds that response once from indexed collection and entry maps. It prepares the version-2 canonical answer-pool value sequence once per collection, reuses the identical hashed payload for every linked element, and applies database duplicate matches as a separate immutable decoration pass. The base model therefore does not repeat pool scans, option validation, or fingerprints after duplicate lookup; element rows retain only selected integer IDs while their values remain owned by the top-level collection. Validation rejects a package above the 5,000 selected-relation aggregate before building this model, bounding both memory and response construction even when many elements share the same 2,000-entry pool.

`apps/frontend-manage/src/components/elements/details/ImportedElementDidacticReview.tsx:ImportedElementDidacticReview` renders the complete applicable authored/scoring review for all nine canonical types: content and explanation; status, base-points, multiplier, and sample-solution settings; choice correctness and feedback; free-text solutions and limits; numerical placeholder, exact/range solutions, and restrictions; selection answers and full answer pool; and case-study items, criteria, cases, solution ranges, and full pool. SC, MC, and KPRIM without a sample solution show one neutral no-scoring-key state and never label nullable correctness as incorrect; the other scoring branches likewise omit absent solution material. The review always warns that packages may contain solutions and copyrighted teaching material and that imported items have no psychometric history and are uncalibrated private `REVIEW` copies. Personal tags remain intentionally absent from the package and review.

The workflow exposes `aria-busy` and polite live status, gives each selection a real accessible checkbox label and 44-pixel touch target, makes the dropzone keyboard-operable, and restores focus to the import/export trigger on close (`apps/frontend-manage/src/components/common/FileUploadDropzone.tsx:FileUploadDropzone`, `apps/frontend-manage/src/pages/index.tsx:Index`). The interactive element preview remains inside Formik state but outside the native import form so Enter in a numerical preview cannot commit the package. Preview triggers expose their controlled/pressed state; opening scrolls and focuses the named preview region, and closing returns focus to the originating trigger.

Export remains fail-closed until the server returns a concrete package preview; a missing preview is shown as a retryable infrastructure failure and cannot enable the download action. Closing the export modal aborts both link creation and package transfer, so stale work cannot trigger a later browser download or notification. Dynamic package warnings are polite live regions, and retry focus moves to the persistent answer-collection overview through loading and settlement. Switching the imported element preview remounts its local review subtree so answer-pool pagination cannot leak between elements.

## Duplicate fingerprints

Fingerprints are internal fields on `Element.importFingerprint` and `AnswerCollection.importFingerprint` (`packages/prisma/src/prisma/schema/element.prisma:Element`, `packages/prisma/src/prisma/schema/resources.prisma:AnswerCollection`). They are indexed with `ownerId` and are deliberately non-unique so users can import duplicate authored content when they choose.

Didactic fingerprint version 2 is defined by the pure `packages/graphql/src/lib/importExportFingerprintCanonicalization.ts` module; media classification remains independently versioned at 1. Element identity includes type, content, explanation, canonical options including solutions/feedback, point settings, normalized answer-pool values, selected values, and verified auto-loading media hashes. It excludes element/collection names, workflow status, tags, owners/permissions, IDs/refs, timestamps, filenames, storage URLs, and collection metadata/history.

The canonicalizer may receive a prepared plain-text answer-pool value sequence. Preparation performs the same package-ref validation and lexical ordering as the direct path, then reuses that frozen sequence without changing the fingerprint payload or version. Direct and prepared paths are regression-tested to produce identical identities.

Answer-collection identity is only its sorted authored entry values. Collection name, description, version/history, entry order, refs, and IDs are excluded. User-activated links and plain entry URLs remain authored content. Verified auto-loading media is represented by SHA-256; external, unavailable, unsupported, or otherwise unpackageable auto-loading media uses the same deterministic omission semantics as portable export. `MediaFile.importFingerprintVersion` makes media classification a tri-state decision: version 1 with a hash is verified package media, version 1 without a hash is a known omission, and a null/mismatched version is unresolved. Free-text solutions and numerical exact/range solutions are sorted and deduplicated as scoring-equivalent sets for identity; distinct Unicode representations remain distinct when the grader treats them as distinct.

Strict package validation and persisted resources share the same semantic canonical form. Package-domain validation may reject malformed transport data; persisted legacy resources instead use a deterministic domain-separated fallback, so every active element and answer collection can finish with a non-null version-2 fingerprint. Duplicate lookup requires didactic version 2; legacy, null, and mismatched versions are ignored, and validation performs no lazy backfill. Imported media persists both the SHA-256 already verified against the package manifest and media-classification version 1. Database refresh loads only `MediaFile.href/contentHash/importFingerprintVersion` for auto-loading references—never blob bytes or Azure APIs—and writes fingerprint/version together with optimistic element, relation, collection-version, and previous-state guards. Normal enabled element authoring locks those dependency rows and rejects lifecycle-marked media, missing rows, owner mismatches, stale media versions, and malformed non-null hashes. A current version-1/null known omission is intentionally authorable and fingerprints to the same deterministic omission representation used by export. While the feature is dark, lifecycle markers remain forbidden but ordinary legacy unresolved media is accepted for mixed-version rollout compatibility and later repaired by the guarded backfill.

Every successful authored element write computes and persists its current didactic fingerprint before the surrounding transaction commits. Answer-entry changes update the collection and every active linked element in deterministic bounded chunks inside the same transaction. Status, tag, permission, and collection-metadata-only changes do not alter identity and retain their existing current fingerprint. Hatchet refresh is repair-only and is not part of the correctness path for a successful authored write.

For active elements and answer collections, either a null fingerprint or a null/mismatched didactic version is dirty and eligible for repair. A current version with a null fingerprint is not a terminal processed state. Soft-deleted resources are outside the active-resource invariant.

`packages/graphql/src/services/importExportFingerprintMaintenance.ts:repairStaleImportExportFingerprints` provides a defense-in-depth safety net for unexpected manual or historical drift. The normal general worker runs `repair-import-export-fingerprints` every 15 minutes with a ten-minute execution timeout, an eight-minute cooperative work budget, and one active run at a time; a duplicate cron is cancelled rather than displacing or overlapping an active run. One invocation handles answer collections and then elements, at most five 100-row batches of each; every cron invocation starts again from the lowest still-dirty IDs. The handler checks elapsed time and Hatchet cancellation between ten-row chunks and 100-row batches, preserves exact processed counts, and performs fresh backlog rechecks before returning. It reports only processed counts, fresh backlog booleans, and whether it stopped early—never authored content or resource IDs. Repair uses no immediate Hatchet retry; durable dirty rows are reconsidered by the next 15-minute cron without extending a run past its cadence.

The scheduled repair is not the rollout migration. `./util/import-export-backfill.sh stg|prd` runs the protected historical sequence: the first media page atomically invalidates every active element once by changing only `importFingerprint` and `importFingerprintVersion`, media classification v1 then completes in bounded batches, a full active-row didactic fingerprint v2 rescan follows, and an invariant-only zero-row verification closes the run. Rollout-wide and targeted media invalidations store the transaction's monotonic ID as a 64-hex dirty token with a null didactic version. Every later transaction therefore presents a different optimistic-write state instead of returning to a previously observed null tuple (the ABA case). These invalidations deliberately preserve authored `Element.version` and `updatedAt`, so deployment maintenance cannot make activity instances appear outdated or fabricate user edits. Each media, didactic, or constraint-validation process holds the same rollout advisory mutex on a dedicated PostgreSQL session; the backfills also retain keyset cursors, bounded batches/concurrency, conditional writes, and database-identity-bound versioned resume manifests under `~/.klicker/import-export-backfill/<environment>`. Old application and worker images must drain before this pass, and private preview remains disabled until the verifier reports zero active null/stale elements and collections plus zero stale media classifications. The 15-minute repair does not replace that rollout evidence.

## Media behavior

`packages/graphql/src/lib/importExportMediaReferences.ts` is the stable public facade for this policy. CommonMark parsing/rewriting lives in `importExportMarkdownMediaReferences.ts`, typed element and answer-collection traversal in `importExportElementMediaReferences.ts`, aggregate work enforcement in `importExportMediaReferenceBudget.ts`, and their shared contracts in `importExportMediaReferenceTypes.ts`. The implementation parses the same CommonMark structure used by the UI and classifies auto-loading images separately from ordinary links. Element content, explanations, choice values/feedback, and case descriptions use the element collector; grading and structural strings such as free-text solutions, units, labels, IDs, and titles remain plain authored data. Answer-collection descriptions use the same CommonMark classifier, while answer-entry values are plain text and contribute only plain URL references. Preview, export, exact closure, import staging/rewriting, and fingerprint media lookup cover both elements and their required collections through this shared policy. Export bundles only auto-loading Klicker-owned blobs from the configured storage account. Package serialization rewrites each verified auto-loading image use to its package-local media ref and replaces every external, unavailable, oversized, or unsupported auto-loading image with a visible, locale-neutral non-loading omission marker. The rewrite is reference-kind-aware: definitions that become image-only and unused are removed, while ordinary user-activated links—including a link or shared definition using the same URL—retain their authored destination. The server and preview therefore neither fetch arbitrary external URLs nor retain dormant image-only source URLs.

Packaged media uses package-local `klicker-package-media://...` references and includes content type, positive byte size, SHA-256, and a canonical `media/<filename>` path in the manifest. Every package-media reference must have exactly one declaration; declaration refs, files, and source hrefs are unique. Empty files are rejected by the manifest contract, parser, and staging boundary so import and later export agree on the media contract. Distinct bounded files may have the same digest and are each verified; content-addressed import staging safely reuses the resulting media identity. Import selects only media required by the chosen elements, creates an exact `RESERVED` ledger before copy, verifies size/hash, copies exclusively, and CASes the row through `COPIED` to `FINALIZED` in the resource transaction. A retry fences prior-operation targets as `CLEANUP_PENDING`; cleanup owns those exact targets even if a crash occurred after storage accepted bytes but before `COPIED` was recorded. Existing unhashed media is reused only after bounded byte verification, and concurrent deduplication never overwrites a conflicting hash. A cleanup failure leaves its ledger and returns `IMPORT_CLEANUP_PENDING` without making the committed import retryable. Local development has an equivalent exclusive file provider and a canonical committed-`MediaFile` route that remains valid after short-lived receipt history expires; production continues to use Azure. Export coalesces aliases of the same storage target but retains distinct storage objects even when their bytes match, keeping preview and final archive accounting identical. Supported media content types are centralized in `packages/graphql/src/lib/mediaContentTypes.ts`; unsupported package media is not bundled on export and is rejected on import.

Direct Manage media-library uploads also establish media identity before an uploaded href can enter authored content. The shared browser/server absolute limit is 256 MiB, which keeps the pinned Azure SDK on its single `Put Blob` path; the browser rejects larger files before requesting a SAS, and finalization independently enforces that limit from Azure's observed `contentLength`, so a custom authenticated client cannot make an oversized object durable. Accepted files upload with the owner-scoped, 15-minute create-only SAS, then call the full-access authenticated `finalizeFileUpload` mutation with the server-created `mediaFileId`; create-only permission prevents reuse of the still-live SAS from changing bytes after hashing. The new `MediaFile` carries a one-shot `direct-upload-pending:<mediaId>` `originalId`. `packages/graphql/src/services/importExportFingerprints.ts:finalizeUploadedMediaFingerprintV1` rechecks ownership and the canonical stored object. Supported media through the 5 MiB package-media limit receives its SHA-256; a valid 5–256 MiB object receives current media version 1 with a null hash as a deterministic known export omission. Missing, zero/indeterminate-length, malformed, or larger-than-256-MiB objects return `false` and retain the pending marker for retry/cleanup. A rollout backfill can observe a new row before Azure exposes the just-uploaded blob; it excludes lifecycle-marked rows, while explicit finalization retries until the blob becomes visible. Normal direct finalization performs no element scan because every element-authoring transaction locks first-party media dependencies and always rejects pending/cleanup lifecycle markers. With import/export enabled it additionally rejects missing rows, stale versions, owner mismatches, and malformed hashes; current version-1/null known omissions remain authorable but export as the stable omission marker. While the feature is dark, ordinary legacy missing/stale media remains editable for mixed-version rollout compatibility, but lifecycle markers are still rejected. An unmarked historical or previously classified row may already be referenced, so a state transition for that row runs one targeted active-element scan and synchronously refreshes the returned IDs in the same transaction. Imported-media staging uses the same targeted repair when verified package bytes upgrade an existing null hash or stale media version. Both repair paths change only fingerprint fields and preserve authored `Element.version` and `updatedAt`; idempotent retries skip the scan. Scheduled fingerprint repair remains defense-in-depth for unexpected drift rather than the correctness boundary. Export uses the same canonical href resolution and accepts bundled-media metadata only from a matching-owner, current media-v1 row with a valid persisted SHA-256; it hashes downloaded bytes against that value and fails closed on drift. Media reads dispatch from the canonical href's actual local/Azure source rather than the package-storage default, so local import-package storage can coexist with the Media Library's Azure direct uploads. Manage makes at most three finalization calls with the same `mediaFileId`, using short bounded backoff after a `false` result or rejected call; only a successful result passes the href to the editor. `getUserMediaFiles` always hides pending and cleanup lifecycle rows; while import/export is enabled it also hides other unclassified rows, whereas the dark gate preserves ordinary legacy visibility. Exhausted retries leave the pending row hidden and show the existing localized upload failure. The subsequent media-library refetch is best-effort because a cache refresh failure must not report an already durable upload as failed or invite a duplicate upload.

All production package and imported-media Azure I/O is centralized in `packages/graphql/src/services/importExportAzureBlobStorage.ts`. `packages/graphql/src/services/importExportStorageDeadline.ts:withImportExportStorageDeadline` passes one abort signal through each SDK/fetch operation and independently races the returned promise, so a stalled provider, retry loop, response body, or non-cooperative test double cannot hold a request or maintenance batch forever. Metadata/control-plane work defaults to 10 seconds; blob transfers, deletes, and SAS round-trip fetches default to 60 seconds. Deadline expiry is always `IMPORT_EXPORT_INFRASTRUCTURE_FAILURE`, never an invalid-package outcome. Media-hash backfill stops without persisting an omission/hash when storage is indeterminate, while cleanup retains its exact `CLEANUP_PENDING` ledger for retry. Azure creation of a new imported-media target is rejected unless the durable `RESERVED` row already exists; this prevents an untracked late write. `packages/graphql/src/services/packageStorage.ts` emits paired privacy-safe `started` and terminal events for actual package upload, replay, export storage, and download spans with one correlation ID, bounded bytes/duration, and stable timeout/failure codes; it never includes an owner, artifact, blob name, URL, or raw exception.

SVG files are deliberately not bundled in import/export packages until a sanitizer exists. A first-party SVG referenced by an element or answer-collection description produces a media warning and its auto-loading image is replaced with the same visible omission marker during package serialization and import preview; ordinary user-activated links remain unchanged.

## Durable state and retention

The durable persistence layer uses `ImportExportPackageArtifact`, `ElementImportReceipt`, and `ImportMediaStaging` plus per-owner quota reservation, atomic expired-lease claims, renewable owner- and lease-bound receipt heartbeats, lease-conditioned completion, and bounded cleanup-candidate queries. Package artifacts retain exact storage targets and expire after 24 hours; completed receipts retain immutable artifact/package/selection identity after the short-lived artifact row is removed. A running import renews its five-minute PostgreSQL receipt lease while it reconciles staging, downloads, stages media, and commits; an expired, replaced, or unrenewable lease fences that execution before its next storage or database side effect. Staging rows distinguish reserved, copied, finalized, and cleanup-pending blob targets. Database triggers reject cross-owner links and immutable-owner changes. Deleting a user or receipt is restricted until its exact artifact/staging cleanup records have been processed; deleting or transferring a media record detaches only the optional media relation and preserves the cleanup ledger.

Package artifacts are used throughout prepare, upload, export, download, quota, and cleanup. Validation tokens bind `{userId, artifactId, packageHash, expiry, jti}` and resolve at most 100 unique selected refs into a canonical selection digest before work; ordering and duplicate input refs do not change that identity. A matching COMPLETE receipt returns its stored result even after token/artifact expiry and without consuming another import quota slot. An active PENDING lease returns `IMPORT_IN_PROGRESS`; an expired lease has one compare-and-set claimant, and identity or selection disagreement returns `IMPORT_REPLAY_MISMATCH`. Resource rows, finalized media ledgers, created-ID arrays, and receipt completion commit in one transaction. Import builds one immutable execution plan before that transaction, prepares each answer-pool fingerprint once, creates entries in bounded 500-row batches, requeries all created entries once, creates elements in bounded 25-row batches without assuming return order, and batches private owner permissions and activity logs. Selection and case-study relations are resolved only through maps of rows created by that execution. Cache invalidations are deferred until commit. Post-commit invalidation and cleanup-warning lookups are fail-soft so committed work is never reported as failed. The follow-up receipt-identity migration prevents rebinding the token identity fields while still allowing artifact expiry to detach the optional live relation. Deploy all additive migrations with both feature gates off using the target-audit and large-table procedure in [Data & Migrations](./data-and-migrations.md#importexport-additive-migration).

The dedicated package HTTP adapter exposes only Prisma, the import/export Redis client, and the authenticated user to package services. Request/response objects, assessment Redis, PubSub, emitters, Hatchet, and unrelated tasks do not cross that feature boundary. Upload streams are binary `Uint8Array` iterables with a route-level body deadline.

## Runtime requirements

User-facing import/export is dark unless `IMPORT_EXPORT_ENABLED=true`. `ASSESSMENT_MODE=true` always disables the feature, even if the master gate is accidentally enabled. `IMPORT_EXPORT_PRIVATE_PREVIEW_ONLY` defaults to `true` outside development/test and limits access to full-access users whose authoritative `User.privatePreview` value is true. Missing or malformed runtime values fail closed; backend startup rejects malformed booleans.

The authenticated `canUseElementImportExport` root capability combines those process gates with role, login scope, and the persisted private-preview flag. Manage requests it with `UserProfile`, renders neither entry point nor modal until the value is exactly `true`, and dynamically loads both package modals. Every prepare, validate, import, preview, and export service checks the same authorization again before rate limiting, database-domain reads, token parsing, or storage access.

Export requires effective `ADMIN` or `OWNER` permission on every selected element and linked answer collection. `WRITE` and `READ` are insufficient, and missing versus unauthorized resources remain indistinguishable.

Preview and final export load the same complete authored payload through bounded, count-first queries. Element scalars and selected-answer relations are loaded in batches of 20; per-element and 5,000-relation aggregate counts plus answer-collection entry counts are checked before relation or entry rows are materialized. Collection entry reads reapply deletion and `ADMIN`/`OWNER` authorization, and a final source-stability check rejects a concurrent permission, deletion, version, metadata, or entry-count change rather than assembling a mixed-state package. Publication locking applies the same aggregate bounds and locks at most the accepted maximum plus one row when proving a source changed.

Before CommonMark parsing, both portable export-plan construction and untrusted import-package dependency validation perform one linear scan of media-bearing element and answer-collection fields. They accept at most 5,000 aggregate media/reference candidate occurrences and 20,000 Markdown delimiter work units. Exceeding either budget fails with `EXPORT_AGGREGATE_LIMIT` on export or `IMPORT_AGGREGATE_LIMIT` on import before media inventory, exact-closure classification, or rewrite work. The work budget is deliberately conservative and counts candidate Markdown syntax inside code because its purpose is to bound parser work, not to classify final references. Plain-text answer-entry values contribute URL candidates but no Markdown work units because they never enter the CommonMark parser.

First-party media references are canonicalized by storage container and blob before any metadata or download I/O, so query-string aliases share one bounded storage operation and rewrite to one package media ref. The parser-work budget is separate from the limit of 100 unique canonical media targets. Media database rows are fetched in one batch, and blob-property work is capped at four concurrent calls. Unknown, unsafe, non-positive, inaccessible, unsupported, and oversized media lengths are omitted consistently by preview and final export. Preview accounts for the actual scoring/didactic fields, collection/item refs, rewritten media, warnings, manifest paths, filenames, and ZIP overhead; rendering stops as soon as the running stored-ZIP size crosses the exact final byte cap, before allocating later files.

Import preparation accepts the exact ZIP byte count, reserves a caller-owned `ImportExportPackageArtifact`, and returns an owner/artifact/byte-bound HMAC capability valid for at most 15 minutes. The browser uploads through the authenticated backend route with cookies and the capability header; it never receives Azure write credentials. The route accepts only the exact manage origin, full-access feature capability, `application/zip`, an exact bounded `Content-Length`, an available upload rate-limit slot, and an available renewable upload-concurrency lease before consuming the request stream. Uploads default to one live body per user and four globally. Rejected origins receive no credentialed CORS reflection. When a rejection leaves request bytes unread, the response disables keep-alive and destroys the unread request stream after the response finishes. The service hashes/counts each body into one preallocated bounded buffer, rejects short or oversized bodies, writes only the canonical `imports/<owner>/<artifact>.zip` target, and conditionally transitions `PENDING → UPLOADING → READY`. A lost successful response can replay the READY result without overwriting storage or consuming a live-work lease. Validation signs a strict purpose/version-separated artifact token whose expiry is the earlier of the normal token TTL and artifact expiry; final import never accepts a raw blob name.

Imports and exports share a serialized per-owner quota of at most 10 unexpired artifact ledgers and 100 MiB reserved bytes. Export reserves the full package cap before source work, shrinks the pending reservation to the exact archive size, then server-writes the canonical target and persists exact bytes/SHA-256. It returns a short-lived HTTPS read-only SAS with private `no-store` behavior; local development uses an authenticated owner-bound download capability. The client never reuses a prior export link: each download re-enters backend authorization, current-state validation, rate/concurrency controls, and quota reservation. A failure whose storage was verified clean deletes its ledger. If a write or compensating delete crosses its deadline, `packages/graphql/src/services/importExportPersistence.ts:markImportExportPackageArtifactStorageUncertain` retains the canonical target, `UPLOADING` state, and full byte/count reservation until expiry-driven cleanup. This prevents a late provider completion from becoming an untracked blob and prevents repeated infrastructure failures from bypassing quota.

Hourly cleanup queries package artifacts, import-media staging ledgers, retained receipts, and exact direct-upload lifecycle rows; it never enumerates a container/prefix or treats a receipt as deletion authority. Import-media candidates exclude active receipt leases and are atomically claimed as `CLEANUP_PENDING` before exact storage deletion, so cleanup cannot race an import finalizer; even `RESERVED/createdBlob=false` targets use deadline-bounded `deleteIfExists` to close the post-copy/pre-CAS crash window. A direct upload becomes eligible one hour after row creation, safely beyond its 15-minute SAS. Cleanup validates the exact marker, owner, canonical Azure href, and age, then compare-and-sets `direct-upload-pending:<id>` to `direct-upload-cleanup:<id>` before deleting that exact blob and finally the exact claimed row. A concurrent upload finalizer that clears the pending marker wins the CAS and prevents storage deletion; indeterminate blob deletion retains the cleanup marker for retry. Unrecorded same-prefix sentinels, malformed markers, and unrelated containers are therefore outside the deletion set. Storage is deleted before its matching ledger/row; a timeout or provider failure leaves durable retry state. Completed receipts expire after 30 days, while detached PENDING receipts are removed after their artifact, lease, and staging records are gone. Each record has an independent failure boundary, so one poison target cannot starve later packages, media records, direct uploads, or receipts. A run processes at most ten 100-row batches per category and reports deletion, failure, unsafe-target, batch, and remaining-backlog counters; hard cleanup failures make the Hatchet task fail for retry and alerting. Its 45-minute Hatchet timeout contains a 40-minute cooperative work budget: the handler checks cancellation and elapsed time between records and batches, then returns remaining backlog for the next hourly run. Individual 60-second storage deadlines fit inside the five-minute shutdown margin. A single-flight `CANCEL_NEWEST` limit retains the active/retrying cleanup run and cancels a duplicate cron instead of overlapping it. The private storage preflight reuses one stable `preflight/import-export-preflight.txt` target, verifies the read-only HTTPS SAS within the same transfer deadline, and fails readiness if final deletion is indeterminate rather than accumulating random orphan targets.

`apps/backend-docker/src/app.ts:prepareApp` validates the gate syntax on every startup. Package storage and token configuration are required only when user-facing operations are enabled for that process; a dark or assessment backend does not need unused package credentials. Enabled production requires:

- `IMPORT_EXPORT_TOKEN_SECRET`: dedicated HMAC secret for artifact capabilities and import tokens; production fails fast unless it contains at least 32 random bytes. Generate it with a cryptographically secure secret manager, provision the same value to all backend instances, and rotate it only with the feature dark because rotation invalidates outstanding capabilities.
- `IMPORT_EXPORT_PACKAGE_STORAGE=azure`: local package storage is test/development only.
- `APP_ORIGIN_MANAGE`: the canonical HTTPS manage-app origin, with no credentials, path, query, or fragment. HTTP is accepted only in explicit development/test runtimes.
- Azure blob credentials: `BLOB_STORAGE_ACCOUNT_NAME` and `BLOB_STORAGE_ACCESS_KEY`.
- Optional limits/rate/timeout controls: `IMPORT_EXPORT_PACKAGE_PREVIEW_RATE_LIMIT`, `IMPORT_EXPORT_PACKAGE_EXPORT_RATE_LIMIT`, `IMPORT_EXPORT_PACKAGE_UPLOAD_RATE_LIMIT`, `IMPORT_EXPORT_PACKAGE_VALIDATE_RATE_LIMIT`, `IMPORT_EXPORT_PACKAGE_IMPORT_RATE_LIMIT`, `IMPORT_EXPORT_PACKAGE_RATE_LIMIT_WINDOW_SECONDS`, `IMPORT_EXPORT_PACKAGE_PREVIEW_CONCURRENCY`, `IMPORT_EXPORT_PACKAGE_PREVIEW_GLOBAL_CONCURRENCY`, `IMPORT_EXPORT_PACKAGE_UPLOAD_CONCURRENCY`, `IMPORT_EXPORT_PACKAGE_UPLOAD_GLOBAL_CONCURRENCY`, `IMPORT_EXPORT_PACKAGE_VALIDATE_CONCURRENCY`, `IMPORT_EXPORT_PACKAGE_VALIDATE_GLOBAL_CONCURRENCY`, `IMPORT_EXPORT_PACKAGE_EXPORT_CONCURRENCY`, `IMPORT_EXPORT_PACKAGE_EXPORT_GLOBAL_CONCURRENCY`, `IMPORT_EXPORT_PACKAGE_IMPORT_CONCURRENCY`, `IMPORT_EXPORT_PACKAGE_IMPORT_GLOBAL_CONCURRENCY`, `IMPORT_EXPORT_PACKAGE_CONCURRENCY_LEASE_TTL_MS`, `IMPORT_EXPORT_PACKAGE_TTL_HOURS`, `IMPORT_EXPORT_UPLOAD_BODY_TIMEOUT_MS`, `IMPORT_EXPORT_AZURE_METADATA_TIMEOUT_MS`, and `IMPORT_EXPORT_AZURE_TRANSFER_TIMEOUT_MS`. Preview, upload, validation, export, and non-replay import work atomically acquire expiring per-user and global Redis leases and fail closed when Redis is unavailable. Upload and import each default to one live execution per user and four globally; completed upload and exactly-once import replay bypass their live-work leases. Owner-checked heartbeats renew both Redis members; the process also tracks the last confirmed local deadline and fences body/storage work, expensive validation work, or storage side effects after expiry or lost ownership. Export preview checks the live lease before and after snapshot work, around media hydration, and between bounded metadata items, so lost ownership cannot produce a successful preview. Its four-worker metadata pool stops dequeuing after the first failure and waits for already-started reads before the surrounding lease is released.

Startup ownership is derived once from the parsed runtime configuration. A normal backend owns user operations only when the master gate is enabled and then requires package storage plus the token secret. A normal general worker always owns cleanup/fingerprint maintenance, including while the user gate is dark, and requires package storage but not the token secret. Assessment backends and assessment workers own neither import/export responsibility. The worker workflow selector enforces that matrix: production normal workers must explicitly allowlist every required maintenance workflow, while assessment workers reject those workflows.

Committed development and local-test environments enable the master gate explicitly, require private-preview users, and select local package storage. `turbo.json` forwards both gate names. Until `IMPORT_EXPORT_ENABLED=true` reaches a normal backend, the feature remains dark by design. Assessment processes remain disabled by the responsibility matrix even if the master gate is accidentally set.

## Rollout checklist

The repository provides the guarded `./util/import-export-backfill.sh stg|prd` sequence plus environment-specific preflight, diagnostic inspection, strict readiness, constraint-validation, cleanup-dry-run, and canary aliases. They use only the selected environment's standard `DATABASE_URL`; assessment mode remains disabled and is not an import/export operations target. Evidence capture, named ownership, staging soak, and production-preview soak remain release requirements; follow the [production runbook](./import-export-production-runbook.md).

- Run the production preflight after secrets and storage are configured.
- Apply the additive Prisma migration with both feature gates off. For measured-large targets, pre-add the nullable version fields, build the exact indexes concurrently, verify them, and then run `migrate deploy`.
- Drain previous images, run the guarded media → didactic → invariant backfill to zero violations, validate the existing deferred hash/version constraints, and require the strict readiness alias to exit `0` before private preview.
- Verify the package container is private, backend upload CORS accepts only the manage origin, and browser read-only SAS downloads have the required CORS and `private, no-store` behavior.
- Deploy first with `IMPORT_EXPORT_ENABLED=false`; enable `IMPORT_EXPORT_PRIVATE_PREVIEW_ONLY=true` only for named preview users after preflight and backfill evidence is green.
- Deploy the Hatchet cleanup task from `packages/hatchet/src/index.ts` and monitor the structured events emitted through `packages/graphql/src/lib/importExportTelemetry.ts:emitImportExportTelemetry`.
- Keep package size/count/error-code/rate-limit metrics visible before GA; duplicate warnings are UX hints, not import enforcement.
- Rollback keeps the additive schema and cleanup active: disable the feature and roll application images back. Target migration ownership, protected invocation, and evidence remain external release gates.

The database-level non-null/current active-resource constraint is a later post-backfill migration. It is intentionally not shipped with the version-2 application rollout because the previous image must remain compatible during the dark deployment window.
