# Element Import/Export Packages

**Import/export duplicate detection is advisory, not authoritative.** The backend computes internal fingerprints for elements and answer collections to show duplicate warnings, but imports still create the selected elements and their required package dependencies. Users decide by selecting or deselecting preview rows.

## Package format

Element packages are strict ZIP archives produced and parsed by `packages/graphql/src/lib/zip.ts:createZip` and `packages/graphql/src/lib/zip.ts:parseZip`. The parser accepts only root `manifest.json`, declared element JSON files, declared answer collection JSON files, and declared media files. JSON files must contain valid UTF-8; malformed byte sequences are rejected rather than replaced with mutated authored text. The parser rejects directory entries, macOS metadata, non-canonical or duplicate paths, unsupported compression methods or flags, data descriptors, inconsistent EOCD/central/local metadata, overlapping or incomplete local records, trailing compressed/archive bytes, CRC mismatches, unexpected files, and oversized compressed or uncompressed payloads.

The package manifest type is `klicker-element-package` and the current version is `3`, configured in `packages/graphql/src/lib/importExportPackageConfig.ts:IMPORT_EXPORT_PACKAGE_VERSION`. Its strict schemas and canonical paths live in `packages/graphql/src/lib/importExportPackageContract.ts`. A package contains 1–100 elements, at most 50 answer collections, at most 2,000 entries per collection and 5,000 entries overall, at most 5,000 selected answer-entry relations across all elements, at most 100 media files, at most 200 closed-enum warnings, and the configured JSON/media/archive byte limits. Raw warning arrays are bounded before duplicate warning codes are collapsed; import still discards package-authored warnings and derives its own warning set.

Version 3 does not transport source element status or answer-collection version. Supplying either field is invalid. Every imported element starts in `REVIEW`, and every imported answer collection starts at version `1`, regardless of source state. This deliberately models import as a new authored copy rather than an exact workflow/version clone.

Personal element tags are intentionally outside the portable package contract. Exported archives never contain tags, imported elements start untagged, and a package that adds undeclared tag fields is rejected by the strict schema. Normal tag management for authored elements is unchanged.

## Canonical didactic payload

Every package element is validated against `packages/graphql/src/lib/elementDomain.ts:canonicalizeElementDomain`, the same neutral option boundary used by normal authoring. The package schema is a strict discriminated union across `SC`, `MC`, `KPRIM`, `FREE_TEXT`, `NUMERICAL`, `CONTENT`, `FLASHCARD`, `SELECTION`, and `CASE_STUDY`; unknown option fields and type-inapplicable answer-collection relations are rejected. Cross-reference validation then proves that selection/case-study entry refs are unique members of the declared linked collection.

Final export and export preview load the complete scoring/relation payload and validate it before serialization. A legacy source that the current importer would reject produces the stable `ELEMENT_NOT_PORTABLE` outcome rather than an archive that cannot be re-imported. The full per-type invariant and grading rules are documented in [Domain Model](./domain-model.md#canonical-element-domain).

The package carries didactic content, solutions, feedback, point settings, and required answer-pool data. It does **not** carry psychometric observations: participant responses, item statistics, difficulty, discrimination, reliability, validity, calibration, activity instances, analytics, and grading history remain outside the contract. Imported elements are uncalibrated copies in `REVIEW`, not psychometrically equivalent items.

Error and warning transport uses a closed GraphQL enum with localized recovery behavior; packages cannot supply UI messages. See [Import/Export Error Contract](./import-export-error-contract.md).

## Manage review and commit workflow

`apps/frontend-manage/src/lib/elementImportWorkflow.ts:ElementImportWorkflowState` makes upload a tested `idle → uploading → validating → reviewing → importing → success/error` reducer workflow. `apps/frontend-manage/src/components/elements/manipulation/UploadModal.tsx:UploadModal` owns one abort controller and monotonically increasing request generation: closing during upload or validation aborts the request, and a late completion from an invalidated generation cannot reopen or replace the current review. Drops and replacements stay disabled through upload, validation, import commit, and the post-commit list refresh.

The final import mutation is the commit boundary. `UploadModal` owns that mutation and the subsequent list refresh; while either is pending it removes the close/cancel actions and disables Escape dismissal. A mutation failure returns the same selection to review with a focused inline error. Mutation success moves irreversibly to the success state before refreshing the element list. A failed post-commit refresh therefore shows localized committed-success and reload guidance with no import action, not a retryable import failure that could invite a duplicate commit. `ImportedElementsOverviewTable` owns selection and presentation only.

The review is driven by the current Formik selection rather than package totals. `ImportedElementsOverviewTable` recomputes the selected duplicate count and required answer collections after every toggle and provides select-all, select-none, and exclude-existing-match actions. `apps/frontend-manage/src/components/elements/manipulation/PackageAnswerCollectionOverview.tsx:PackageAnswerCollectionOverview` shows only collections needed by the current selection and mounts their complete entry lists only when the lecturer expands them. The didactic answer pool follows the same lazy-mount rule, so a valid 2,000-entry closed pool does not create hidden list nodes. One semantic responsive list is shared across breakpoints; there are no separate desktop/mobile selection trees that can drift apart.

The validation response transports each full answer pool exactly once under top-level `answerCollections`. Per-element preview rows carry only `answerCollectionRef` and selected `answerCollectionItemIds`; `packages/graphql/src/schema/element.ts:ElementImportPackagePreviewElement` does not expose repeated entry/value arrays. Its `options` field is the nine-member `ElementImportPackagePreviewOptions` union defined in `packages/graphql/src/schema/elementImportPreviewOptions.ts`, never the `Json` scalar. Generated clients therefore discriminate SC, MC, KPRIM, numerical, free-text, content, flashcard, selection, and case-study payloads by `__typename`; choice correctness remains nullable when no sample solution exists, and numerical placeholders—including Unicode text—are transported as authored. `apps/frontend-manage/src/lib/elementImportPreview.ts:createElementImportReviewModel` exhaustively converts that union and derives each preview's complete pool from the top-level ref map without `any` or JSON casts. This prevents a valid 100-element package sharing one 2,000-entry collection from multiplying the same authored values across the GraphQL response.

`packages/graphql/src/services/elementImportPreviewModel.ts` builds that response once from indexed collection and entry maps. It prepares the version-1 canonical answer-pool value sequence once per collection, reuses the identical hashed payload for every linked element, and applies database duplicate matches as a separate immutable decoration pass. The base model therefore does not repeat pool scans, option validation, or fingerprints after duplicate lookup; element rows retain only selected integer IDs while their values remain owned by the top-level collection. Validation rejects a package above the 5,000 selected-relation aggregate before building this model, bounding both memory and response construction even when many elements share the same 2,000-entry pool.

`apps/frontend-manage/src/components/elements/details/ImportedElementDidacticReview.tsx:ImportedElementDidacticReview` renders the complete applicable authored/scoring review for all nine canonical types: content and explanation; status, base-points, multiplier, and sample-solution settings; choice correctness and feedback; free-text solutions and limits; numerical placeholder, exact/range solutions, and restrictions; selection answers and full answer pool; and case-study items, criteria, cases, solution ranges, and full pool. SC, MC, and KPRIM without a sample solution show one neutral no-scoring-key state and never label nullable correctness as incorrect; the other scoring branches likewise omit absent solution material. The review always warns that packages may contain solutions and copyrighted teaching material and that imported items have no psychometric history and are uncalibrated private `REVIEW` copies. Personal tags remain intentionally absent from the package and review.

The workflow exposes `aria-busy` and polite live status, gives each selection a real accessible checkbox label, makes the dropzone keyboard-operable, and restores focus to the import/export trigger on close (`apps/frontend-manage/src/components/common/MediaLibrary.tsx:MediaUploadDropzone`, `apps/frontend-manage/src/pages/index.tsx:Index`). The document language follows the active English/German locale through `apps/frontend-manage/src/pages/_document.tsx:Document`.

## Duplicate fingerprints

Fingerprints are internal fields on `Element.importFingerprint` and `AnswerCollection.importFingerprint` (`packages/prisma/src/prisma/schema/element.prisma:Element`, `packages/prisma/src/prisma/schema/resources.prisma:AnswerCollection`). They are indexed with `ownerId` and are deliberately non-unique so users can import duplicate authored content when they choose.

Fingerprint version 1 is defined by the pure `packages/graphql/src/lib/importExportFingerprintCanonicalization.ts` module. Element identity includes type, content, explanation, canonical options including solutions/feedback, point settings, normalized answer-pool values, selected values, and verified auto-loading media hashes. It excludes element/collection names, workflow status, tags, owners/permissions, IDs/refs, timestamps, filenames, storage URLs, and collection metadata/history.

The canonicalizer may receive a prepared plain-text answer-pool value sequence. Preparation performs the same package-ref validation and lexical ordering as the original version-1 path, then reuses that frozen sequence without changing the fingerprint payload or version. Direct and prepared paths are regression-tested to produce identical identities.

Answer-collection identity is only its sorted authored entry values. Collection name, description, version/history, entry order, refs, and IDs are excluded. User-activated links and plain entry URLs remain authored content. Verified auto-loading media is represented by SHA-256; external/unpackaged auto-loading media uses one omission marker. `MediaFile.importFingerprintVersion` makes this a tri-state decision: version 1 with a hash is verified package media, version 1 without a hash is a known omission, and a null/mismatched version is unresolved and yields no fingerprint. A package transport ref or unknown relation ID/ref likewise yields no fingerprint instead of embedding unstable identity. Free-text solutions and numerical exact/range solutions are sorted and deduplicated as scoring-equivalent sets for identity.

The package and database adapters feed the same pure function. Duplicate lookup requires `importFingerprintVersion = 1`; legacy, null, and mismatched versions are ignored, and validation performs no lazy backfill. Imported media persists both the SHA-256 already verified against the package manifest and media decision version 1. Database refresh loads only `MediaFile.href/contentHash/importFingerprintVersion` for auto-loading references—never blob bytes or Azure APIs—and writes fingerprint/version together with optimistic element, relation, collection-version, and previous-state guards.

Element didactic writes mark the row dirty and recompute DB-only identity. Status, tag, and collection-metadata changes do not alter identity. Answer-entry changes atomically increment the collection version, null the collection fingerprint/version, and dirty all linked elements with one `updateMany`; after commit they fire-and-forget one bounded Hatchet refresh. Enqueue failure never rolls back the authored write because null fields are durable retry markers. Historical media and fingerprint backfills are protected CLI operations with advisory locks, keyset cursors, bounded batches/concurrency, conditional writes, and persisted resume manifests; permanently unresolved early rows cannot trap later rows. Media maintenance classifies supported bounded media as version 1 plus its hash and unsupported, inaccessible, or oversized media as a version-1 omission before fingerprint backfill runs.

## Media behavior

`packages/graphql/src/lib/importExportMediaReferences.ts` parses the same CommonMark structure used by the UI and classifies auto-loading images separately from ordinary links. Element content, explanations, choice values/feedback, and case descriptions use the element collector; grading and structural strings such as free-text solutions, units, labels, IDs, and titles remain plain authored data. Answer-collection descriptions use the same CommonMark classifier, while answer-entry values are plain text and contribute only plain URL references. Preview, export, exact closure, import staging/rewriting, and fingerprint media lookup cover both elements and their required collections through this shared policy. Export bundles only auto-loading Klicker-owned blobs from the configured storage account. Package serialization rewrites each verified auto-loading image use to its package-local media ref and replaces every external, unavailable, oversized, or unsupported auto-loading image with a visible, locale-neutral non-loading omission marker. The rewrite is reference-kind-aware: definitions that become image-only and unused are removed, while ordinary user-activated links—including a link or shared definition using the same URL—retain their authored destination. The server and preview therefore neither fetch arbitrary external URLs nor retain dormant image-only source URLs.

Packaged media uses package-local `klicker-package-media://...` references and includes content type, byte size, SHA-256, and a canonical `media/<filename>` path in the manifest. Every package-media reference must have exactly one declaration; declaration refs, files, and source hrefs are unique. Distinct bounded files may have the same digest and are each verified; content-addressed import staging safely reuses the resulting media identity. Import selects only media required by the chosen elements, creates an exact `RESERVED` ledger before copy, verifies size/hash, copies exclusively, and CASes the row through `COPIED` to `FINALIZED` in the resource transaction. A retry fences prior-operation targets as `CLEANUP_PENDING`; cleanup owns those exact targets even if a crash occurred after storage accepted bytes but before `COPIED` was recorded. Existing unhashed media is reused only after bounded byte verification, and concurrent deduplication never overwrites a conflicting hash. A cleanup failure leaves its ledger and returns `IMPORT_CLEANUP_PENDING` without making the committed import retryable. Local development has an equivalent exclusive file provider and a canonical committed-`MediaFile` route that remains valid after short-lived receipt history expires; production continues to use Azure. Export coalesces aliases of the same storage target but retains distinct storage objects even when their bytes match, keeping preview and final archive accounting identical. Supported media content types are centralized in `packages/graphql/src/lib/mediaContentTypes.ts`; unsupported package media is not bundled on export and is rejected on import.

All production package and imported-media Azure I/O is centralized in `packages/graphql/src/services/importExportAzureBlobStorage.ts`. `packages/graphql/src/services/importExportStorageDeadline.ts:withImportExportStorageDeadline` passes one abort signal through each SDK/fetch operation and independently races the returned promise, so a stalled provider, retry loop, response body, or non-cooperative test double cannot hold a request or maintenance batch forever. Metadata/control-plane work defaults to 10 seconds; blob transfers, deletes, and SAS round-trip fetches default to 60 seconds. Deadline expiry is always `IMPORT_EXPORT_INFRASTRUCTURE_FAILURE`, never an invalid-package outcome. Media-hash backfill stops without persisting an omission/hash when storage is indeterminate, while cleanup retains its exact `CLEANUP_PENDING` ledger for retry. Azure creation of a new imported-media target is rejected unless the durable `RESERVED` row already exists; this prevents an untracked late write. `packages/graphql/src/services/packageStorage.ts` emits paired privacy-safe `started` and terminal events for actual package upload, replay, export storage, and download spans with one correlation ID, bounded bytes/duration, and stable timeout/failure codes; it never includes an owner, artifact, blob name, URL, or raw exception.

SVG files are deliberately not bundled in import/export packages until a sanitizer exists. A first-party SVG referenced by an element or answer-collection description produces a media warning and its auto-loading image is replaced with the same visible omission marker during package serialization and import preview; ordinary user-activated links remain unchanged.

## Durable state and retention

The durable persistence layer uses `ImportExportPackageArtifact`, `ElementImportReceipt`, and `ImportMediaStaging` plus per-owner quota reservation, atomic expired-lease claims, lease-conditioned completion, and bounded cleanup-candidate queries. Package artifacts retain exact storage targets and expire after 24 hours; completed receipts retain immutable artifact/package/selection identity after the short-lived artifact row is removed. Staging rows distinguish reserved, copied, finalized, and cleanup-pending blob targets. Database triggers reject cross-owner links and immutable-owner changes. Deleting a user or receipt is restricted until its exact artifact/staging cleanup records have been processed; deleting or transferring a media record detaches only the optional media relation and preserves the cleanup ledger.

Package artifacts are used throughout prepare, upload, export, download, quota, and cleanup. Validation tokens bind `{userId, artifactId, packageHash, expiry, jti}` and resolve at most 100 unique selected refs into a canonical selection digest before work; ordering and duplicate input refs do not change that identity. A matching COMPLETE receipt returns its stored result even after token/artifact expiry and without consuming another import quota slot. An active PENDING lease returns `IMPORT_IN_PROGRESS`; an expired lease has one compare-and-set claimant, and identity or selection disagreement returns `IMPORT_REPLAY_MISMATCH`. Resource rows, finalized media ledgers, created-ID arrays, and receipt completion commit in one transaction. Import builds one immutable execution plan before that transaction, prepares each answer-pool fingerprint once, creates entries in bounded 500-row batches, requeries all created entries once, creates elements in bounded 25-row batches without assuming return order, and batches private owner permissions and activity logs. Selection and case-study relations are resolved only through maps of rows created by that execution. Cache invalidations are deferred until commit. Post-commit invalidation and cleanup-warning lookups are fail-soft so committed work is never reported as failed. The follow-up receipt-identity migration prevents rebinding the token identity fields while still allowing artifact expiry to detach the optional live relation. Deploy all additive migrations with both feature gates off using the target-audit and large-table procedure in [Data & Migrations](./data-and-migrations.md#importexport-additive-migration).

## Runtime requirements

User-facing import/export is dark unless `IMPORT_EXPORT_ENABLED=true`. `ASSESSMENT_MODE=true` always disables the feature, even if the master gate is accidentally enabled. `IMPORT_EXPORT_PRIVATE_PREVIEW_ONLY` defaults to `true` outside development/test and limits access to full-access users whose authoritative `User.privatePreview` value is true. Missing or malformed runtime values fail closed; backend startup rejects malformed booleans.

The authenticated `canUseElementImportExport` root capability combines those process gates with role, login scope, and the persisted private-preview flag. Manage requests it with `UserProfile`, renders neither entry point nor modal until the value is exactly `true`, and dynamically loads both package modals. Every prepare, validate, import, preview, and export service checks the same authorization again before rate limiting, database-domain reads, token parsing, or storage access.

Export requires effective `ADMIN` or `OWNER` permission on every selected element and linked answer collection. `WRITE` and `READ` are insufficient, and missing versus unauthorized resources remain indistinguishable.

Preview and final export load the same complete authored payload through bounded, count-first queries. Element scalars and selected-answer relations are loaded in batches of 20; per-element and 5,000-relation aggregate counts plus answer-collection entry counts are checked before relation or entry rows are materialized. Collection entry reads reapply deletion and `ADMIN`/`OWNER` authorization, and a final source-stability check rejects a concurrent permission, deletion, version, metadata, or entry-count change rather than assembling a mixed-state package. Publication locking applies the same aggregate bounds and locks at most the accepted maximum plus one row when proving a source changed.

Before CommonMark parsing, both portable export-plan construction and untrusted import-package dependency validation perform one linear scan of media-bearing element and answer-collection fields. They accept at most 5,000 aggregate media/reference candidate occurrences and 20,000 Markdown delimiter work units. Exceeding either budget fails with `EXPORT_AGGREGATE_LIMIT` on export or `IMPORT_AGGREGATE_LIMIT` on import before media inventory, exact-closure classification, or rewrite work. The work budget is deliberately conservative and counts candidate Markdown syntax inside code because its purpose is to bound parser work, not to classify final references. Plain-text answer-entry values contribute URL candidates but no Markdown work units because they never enter the CommonMark parser.

First-party media references are canonicalized by storage container and blob before any metadata or download I/O, so query-string aliases share one bounded storage operation and rewrite to one package media ref. The parser-work budget is separate from the limit of 100 unique canonical media targets. Media database rows are fetched in one batch, and blob-property work is capped at four concurrent calls. Unknown, unsafe, non-positive, inaccessible, unsupported, and oversized media lengths are omitted consistently by preview and final export. Preview accounts for the actual scoring/didactic fields, collection/item refs, rewritten media, warnings, manifest paths, filenames, and ZIP overhead; rendering stops as soon as the running stored-ZIP size crosses the exact final byte cap, before allocating later files.

Import preparation accepts the exact ZIP byte count, reserves a caller-owned `ImportExportPackageArtifact`, and returns an owner/artifact/byte-bound HMAC capability valid for at most 15 minutes. The browser uploads through the authenticated backend route with cookies and the capability header; it never receives Azure write credentials. The route accepts only the exact manage origin, full-access feature capability, `application/zip`, an exact bounded `Content-Length`, and an available upload rate-limit slot before consuming the request stream. Rejected origins receive no credentialed CORS reflection. When a rejection leaves request bytes unread, the response disables keep-alive and destroys the unread request stream after the response finishes. The service hashes/counts the body, rejects short or oversized bodies, writes only the canonical `imports/<owner>/<artifact>.zip` target, and conditionally transitions `PENDING → UPLOADING → READY`. A lost successful response can replay the READY result without overwriting storage. Validation signs a strict purpose/version-separated artifact token whose expiry is the earlier of the normal token TTL and artifact expiry; final import never accepts a raw blob name.

Imports and exports share a serialized per-owner quota of at most 10 unexpired artifact ledgers and 100 MiB reserved bytes. Export reserves the full package cap before source work, shrinks the pending reservation to the exact archive size, then server-writes the canonical target and persists exact bytes/SHA-256. It returns a short-lived HTTPS read-only SAS with private `no-store` behavior; local development uses an authenticated owner-bound download capability. The client never reuses a prior export link: each download re-enters backend authorization, current-state validation, rate/concurrency controls, and quota reservation. A failure whose storage was verified clean deletes its ledger. If a write or compensating delete crosses its deadline, `packages/graphql/src/services/importExportPersistence.ts:markImportExportPackageArtifactStorageUncertain` retains the canonical target, `UPLOADING` state, and full byte/count reservation until expiry-driven cleanup. This prevents a late provider completion from becoming an untracked blob and prevents repeated infrastructure failures from bypassing quota.

Hourly cleanup queries artifact and import-media staging records only. It validates each exact canonical target and never enumerates a container/prefix or treats a receipt as deletion authority. Unrecorded same-prefix sentinels and unrelated containers are therefore outside its deletion set. Media candidates exclude active receipt leases and are atomically claimed as `CLEANUP_PENDING` before exact storage deletion, so cleanup cannot race a finalizer; even `RESERVED/createdBlob=false` targets use deadline-bounded `deleteIfExists` to close the post-copy/pre-CAS crash window. Storage is deleted before its matching ledger; a timeout or provider failure leaves the ledger intact. Completed receipts expire after 30 days, while detached PENDING receipts are removed after their artifact, lease, and staging records are gone. Each record has an independent failure boundary, so one poison target cannot starve later packages, media records, or receipts. A run processes at most ten 100-row batches per category and reports deletion, failure, unsafe-target, batch, and remaining-backlog counters; hard cleanup failures make the Hatchet task fail for retry and alerting. The private storage preflight reuses one stable `preflight/import-export-preflight.txt` target, verifies the read-only HTTPS SAS within the same transfer deadline, and fails readiness if final deletion is indeterminate rather than accumulating random orphan targets.

`apps/backend-docker/src/app.ts:prepareApp` validates the gate syntax on every startup. Package storage and token configuration are required only when user-facing operations are enabled for that process; a dark or assessment backend does not need unused package credentials. Enabled production requires:

- `IMPORT_EXPORT_TOKEN_SECRET`: dedicated HMAC secret for artifact capabilities and import tokens; production fails fast unless it contains at least 32 random bytes. Generate it with a cryptographically secure secret manager, provision the same value to all backend instances, and rotate it only with the feature dark because rotation invalidates outstanding capabilities.
- `IMPORT_EXPORT_PACKAGE_STORAGE=azure`: local package storage is test/development only.
- `APP_ORIGIN_MANAGE`: the canonical HTTPS manage-app origin, with no credentials, path, query, or fragment. HTTP is accepted only in explicit development/test runtimes.
- Azure blob credentials: `BLOB_STORAGE_ACCOUNT_NAME` and `BLOB_STORAGE_ACCESS_KEY`.
- Optional limits/rate/timeout controls: `IMPORT_EXPORT_PACKAGE_PREVIEW_RATE_LIMIT`, `IMPORT_EXPORT_PACKAGE_EXPORT_RATE_LIMIT`, `IMPORT_EXPORT_PACKAGE_UPLOAD_RATE_LIMIT`, `IMPORT_EXPORT_PACKAGE_VALIDATE_RATE_LIMIT`, `IMPORT_EXPORT_PACKAGE_IMPORT_RATE_LIMIT`, `IMPORT_EXPORT_PACKAGE_RATE_LIMIT_WINDOW_SECONDS`, `IMPORT_EXPORT_PACKAGE_PREVIEW_CONCURRENCY`, `IMPORT_EXPORT_PACKAGE_EXPORT_CONCURRENCY`, `IMPORT_EXPORT_PACKAGE_PREVIEW_GLOBAL_CONCURRENCY`, `IMPORT_EXPORT_PACKAGE_EXPORT_GLOBAL_CONCURRENCY`, `IMPORT_EXPORT_PACKAGE_CONCURRENCY_LEASE_TTL_MS`, `IMPORT_EXPORT_PACKAGE_TTL_HOURS`, `IMPORT_EXPORT_AZURE_METADATA_TIMEOUT_MS`, and `IMPORT_EXPORT_AZURE_TRANSFER_TIMEOUT_MS`. Preview and export atomically acquire expiring per-user and global Redis leases and fail closed when Redis is unavailable. Owner-checked heartbeats renew both members; the process also tracks the last confirmed local deadline and fences storage side effects after expiry or lost ownership.

Startup ownership is derived once from the parsed runtime configuration. A normal backend owns user operations only when the master gate is enabled and then requires package storage plus the token secret. A normal general worker always owns cleanup/fingerprint maintenance, including while the user gate is dark, and requires package storage but not the token secret. Assessment backends and assessment workers own neither import/export responsibility. The worker workflow selector enforces that matrix: production normal workers must explicitly allowlist every required maintenance workflow, while assessment workers reject those workflows.

Committed development and local-test environments enable the master gate explicitly, require private-preview users, and select local package storage. `turbo.json` forwards both gate names. Until `IMPORT_EXPORT_ENABLED=true` reaches a normal backend, the feature remains dark by design. Assessment processes remain disabled by the responsibility matrix even if the master gate is accidentally set.

## Rollout checklist

The repository provides the environment-specific preflight, inspect, media-hash/fingerprint backfill, constraint-validation, verification, cleanup-dry-run, and canary aliases in `packages/graphql/package.json`. Their execution against an approved target, evidence capture, named ownership, staging soak, and production-preview soak remain release requirements; follow the [production runbook](./import-export-production-runbook.md).

- Run the production preflight after secrets and storage are configured.
- Apply the additive Prisma migration with both feature gates off. For measured-large targets, pre-add the nullable version fields, build the exact indexes concurrently, verify them, and then run `migrate deploy`.
- Backfill and verify media hashes and fingerprints, then validate the deferred hash/version constraints before private preview.
- Verify the package container is private, backend upload CORS accepts only the manage origin, and browser read-only SAS downloads have the required CORS and `private, no-store` behavior.
- Deploy first with `IMPORT_EXPORT_ENABLED=false`; enable `IMPORT_EXPORT_PRIVATE_PREVIEW_ONLY=true` only for named preview users after preflight and backfill evidence is green.
- Deploy the Hatchet cleanup task from `packages/hatchet/src/index.ts` and monitor the structured events emitted through `packages/graphql/src/lib/importExportTelemetry.ts:emitImportExportTelemetry`.
- Keep package size/count/error-code/rate-limit metrics visible before GA; duplicate warnings are UX hints, not import enforcement.
- Rollback keeps the additive schema and cleanup active: disable the feature and roll application images back. Target migration ownership, protected invocation, and evidence remain external release gates.
