# Keep permission revocations fail-closed

`Permission`, group membership, entity ownership, and object-hierarchy relations remain the source of truth, while `DerivedPermission` remains the authorization read model. Permission recomputation stays synchronous until measurements show that set-based SQL is insufficient; asynchronous propagation may then be used for grants only after durable dispatch, persistent failure reporting, reconciliation, and a database fence shared by mutations and workers prevent stale writes. Revokes and downgrades remain synchronous and fail-closed.

## Proposed async contract

Gate A showed that the set-based synchronous path still misses the approved latency SLO, so Slice 4 proposes one database-global PostgreSQL transaction-level advisory lock acquired first by every permission source mutation, synchronous revoke or downgrade, and propagation worker. Each source transaction atomically upserts a canonical work identity—object type and ID plus recompute mode and optional user scope—and increments its generation. The database constrains the deterministic key to that tuple and independently enforces tuple uniqueness. At-least-once workers full-rederive current source state and mark the latest observed generation processed in the same fenced transaction.

Hatchet acceptance advances the dispatched generation only after enqueue, and a one-minute reconciliation cadence redelivers unresolved generations. Repeated mutations preserve the earliest `dirtyAt` and `recoverBy` until all observed work is processed, so churn cannot postpone recovery indefinitely. A persistent database failure record stores a sanitized failure code against the generation the worker actually observed while leaving work unresolved. The proposed maximum grant-convergence SLO is five minutes from the first unresolved mutation. The prototype proves the deadline and deterministic recovery candidates; production approval still requires scheduler and queue instrumentation, lock-wait and throughput measurements, breach alerting, and an external alert path for failures that also prevent writing the database sink.

The global fence is deliberately conservative: it handles overlapping course, activity, element, answer-collection, group, and ownership roots without a fallible lock-order map, but introduces head-of-line blocking between unrelated permission changes. Hatchet concurrency controls and root-scoped locks were rejected as the initial correctness fence because they do not cover synchronous mutations or roots that converge on the same `DerivedPermission` rows. The exact production key representation and schema remain maintainer decisions. This proposed extension remains approval-gated after its database prototype; no production schema or call-site conversion is authorized yet.
